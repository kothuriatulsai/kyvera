# 2026-10-10

## Step 28 — "My tasks" and notifications (ADR 0014)

Every role's experience has been purely reactive since Slice A - you only find out something
needs you by browsing to it. Built two features on top of ADR 0013's visibility module: a
computed, never-stored `GET /me/tasks` per role, and a stored, append-only `Notification` log
for the moments the brief calls out (upload, remark, confirm, approve, reject, member
added/removed), written in the same transaction as the action that causes it. Full design in
ADR 0014.

### The plan's amendments, as built (per review before implementation)

1. **Remarks notify both sides of the thread** (`ENGINEERING` + `PRODUCT_DESIGNER` members, minus
   the actor), not just the designer - a remark is a two-way conversation, not a one-way "your
   turn" ping.
2. **Task logic keys off the latest remark's *author role*, not just whether a remark exists.**
   The designer's "respond" task only fires if the latest remark on the latest unconfirmed version
   wasn't left by a designer; Engineering's "Review" task is suppressed if their own remark was the
   latest one. Tested both directions explicitly (engineer remarks → designer task appears,
   engineer's own task stays suppressed; designer replies → flips back).
3. **A removed member gets no link back into the Project** (ADR 0013 would 404 it the instant they
   tried) - `link: '/'`, with the Project named by code in the message text instead.
4. **Confirming also notifies the Product Designer**, not just Management - their work on that
   version is done either way, confirmed or not yet decided.
5. **`e2e/smoke.spec.ts`** updated for `/` now being "My tasks" - both tests click "Projects"
   explicitly before continuing as before.

### Two real bugs found running the full suite together, not file-by-file

1. **A transaction's single connection can't take two concurrent queries.** The first draft of
   each `notify*` helper resolved two recipient sets with `Promise.all` on the same `tx` client
   (e.g. Product Designer members + every active Management user, for a confirmation). That raced
   intermittently under full-suite load - surfaced as a flaky 500 on `POST .../confirm`, not an
   obvious error message pointing at the cause. Fixed by making every such pair of lookups
   sequential instead.
2. **"Notify every active user of role X" is a genuine cross-test-file race once it's real
   behavior**, not a theoretical one. Test files share one database and (by default) run in
   parallel; a confirm/approve/decide in one file's test can insert a `Notification` row for a
   `MANAGEMENT`/`PMO` test user a *different*, concurrently-running file just created - including
   one that file is mid-cleanup on. First symptom was an intermittent FK violation deleting test
   users (`cleanupTestUsers()` now deletes their `Notification` rows first, but a notification
   landing *during* that delete, from an unrelated file, still raced it). Fixed at the root by
   setting `fileParallelism: false` in `apps/api/vitest.config.ts` - test files now run one at a
   time, which removes the race instead of patching around each symptom it produces.
