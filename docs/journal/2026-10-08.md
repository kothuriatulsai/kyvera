# 2026-10-08

## Step 25 — Refresh-token sessions (ADR 0012)

The access token has been memory-only since day one, on purpose (XSS can't read it out of
`localStorage`), but that meant a reload or a typed URL logged everyone out. Fixed it with the
standard access/refresh split: a short-lived access token (now 15 minutes, down from an hour)
alongside a new opaque refresh token in an `httpOnly`, `SameSite=Strict`, `Path=/auth` cookie,
backed by a new `UserSession` table (`tokenHash`, `previousTokenHash`, `rotatedAt`, `userAgent`,
`createdAt`, `lastUsedAt`, `expiresAt`, `revokedAt`). Full rationale in ADR 0012; highlights below.

### Rotation, reuse detection, and the multi-tab race

`POST /auth/refresh` rotates the secret on every call. A secret that matches neither the current
nor a recently-rotated-away hash revokes the whole session (reuse detection). The approved plan's
first amendment called out the obvious failure mode this creates: two tabs refreshing at the same
moment would both present the same secret, and whichever the server processes second would look
exactly like reuse of a token the first tab already rotated away.

Handled on both ends. Server: the session row keeps `previousTokenHash` + `rotatedAt`; a secret
matching the previous hash within a 60-second grace window rotates again and succeeds instead of
revoking. Client: `AuthProvider` serializes refresh calls across tabs via
`navigator.locks.request('kyvera-refresh', fn)`, falling back to calling `fn()` directly where the
Web Locks API isn't available - the grace window is the real backstop for that case.

### Immediate revocation

Added a `sid` (session id) claim to the access token. `authenticate` / `resolveActor` now does one
extra narrow DB read per request (`sessionService.assertSessionValid`) rejecting the token if its
session is revoked or expired. Without this, logout - or a future "log out everywhere" - would
only take effect once the access token's own 15-minute life ran out on its own; with it, the very
next request after revocation gets a 401.

### Idle timeout vs. absolute limit

Tracked separately, both configurable via env (`REFRESH_IDLE_TIMEOUT_SECONDS`, default 1800;
`REFRESH_ABSOLUTE_TTL_SECONDS`, default 43200). Idle is measured from `lastUsedAt`, which only
moves on a successful refresh - confirmed nothing in the web app polls the API on a timer, since
that would make the idle timeout fake. Absolute is measured against `expiresAt`, fixed at session
creation and never extended by rotation.

### CSRF, CORS, and the rest of the plan's amendments

Origin-header check (`assertAllowedOrigin`) on both `/auth/refresh` and `/auth/logout`, on top of
`SameSite=Strict` - and now also on logout, per the plan's third amendment, which also asked for
`crypto.timingSafeEqual` on the hash comparisons (done - `hashesMatch`, safe here since both sides
are always equal-length SHA-256 hex digests) and that confirmation that nothing polls on a timer.
CORS gained `credentials: true`, still only for the explicit origin allowlist that already refused
wildcards - necessary once credentials are involved, since the browser forbids pairing
`credentials: true` with a wildcard origin anyway. Password change, admin reset, and deactivation
all revoke every session for that user (role change deliberately does not - ADR 0011's existing
403-triggers-resync already handles that case without ending the session). Cleanup is a
`deleteStale()` call on login, not a background job this project has no infrastructure to run.

### Web: silent restore, transparent retry, activity-gated proactive refresh, idle warning

`AuthProvider` gained a `checkingInitialSession` state that renders nothing until a mount-time
`POST /auth/refresh` resolves - a reload never flashes the login page for someone who isn't logged
out. `api/client.ts`'s `rawFetch` now retries once after a successful refresh on a 401, via a
registered handler, before falling through to the existing session-ended handling. A one-shot
timer (not a poll) fires 60 seconds before the access token expires and only actually refreshes if
there's been real activity (`click`/`keydown`/`popstate`, or regaining window focus) since the
last refresh; an idle tab lets it lapse. A second one-shot timer shows a static "you'll be logged
out in about a minute" banner 60 seconds before the idle timeout, with a "Stay signed in" button
that refreshes immediately (the plan's fourth amendment, kept from the original optional item).

### A test-design trap worth remembering

The three new fake-timer tests (`auth.test.tsx`, proactive refresh / idle warning) initially called
`vi.useFakeTimers()` *after* logging in. That's too late: `scheduleTimers`'s `setTimeout` calls had
already been scheduled under real timers during the login flow, so `vi.advanceTimersByTimeAsync`
afterward had nothing real to advance - the tests just timed out waiting for a login heading that,
in two cases, never appeared at all (see below). Fixed by switching to fake timers (with
`shouldAdvanceTime: true`, which keeps React Testing Library's real-time-based `findBy*` polling
working alongside explicit fast-forwarding) *before* `renderApp`, so every timer in the flow -
including the mount-time silent-restore call - is fake from the start.

That exposed a second trap: two of those tests pre-mocked a *successful* `/auth/refresh` response
to assert the later proactive refresh worked - but the mount-time silent-restore effect hits that
exact same endpoint *before* login even happens, so the mocked success silently logged the test in
before `logIn()` ever ran, and the login heading it was waiting for never appeared. Fixed with a
call-counter in the mock: the first call (mount-time restore, no real cookie yet) returns 401, and
only later calls succeed.

## Step 26 — Follow-up: atomic rotation for genuinely concurrent refreshes

Review feedback on Step 25 before merge: `rotateSession` read the session, decided whether the
presented secret was current, then wrote the new hash with a plain `update` - a read-then-write
with no condition tying the write to the state that was read. Two refreshes fired truly
concurrently with the *same* cookie (not the sequential two-tab race Step 25's grace window
already covered, but both in flight at once) could both read the same current hash, both pass
validation, and then blindly overwrite each other's write. Whichever wrote last would win in the
database, leaving the other response's cookie matching neither the current hash nor
`previousTokenHash` - its next use would look exactly like reuse and revoke the session, for a
request that did nothing wrong.

Fixed with a compare-and-swap: `sessionRepository.rotateIfCurrent` (`updateMany` with
`where: { id, tokenHash: expectedTokenHash }`, replacing the old unconditional `rotate`) only
writes if the database's `tokenHash` still matches what `rotateSession` read. `rotateSession` is
now a small retry loop (bounded at 5 attempts, defensive - real races resolve on the first retry):
on a lost race (zero rows written), it re-reads the session and runs the exact same three-way
current/recently-superseded/reuse check against the fresher row, rather than treating "I lost the
database race" as reuse. The loser's own request still succeeds - it just ends up rotating from
the winner's new hash instead of the one it originally read.
