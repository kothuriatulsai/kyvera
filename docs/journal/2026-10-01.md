## Step 13 — SOP Slice A: entity-model ADRs, a storage ADR, and the first migration

Continuing directly from the previous session's read-through of the SOP, the existing
codebase, and ADRs 0001–0005. That session produced a first-draft ADR 0006 (SOP entity

let alone migrated. This entry covers the corrections, the storage ADR they required, and

### Part 0 — Keeping the private sources private, everywhere, not just in README

While reviewing the draft ADRs, both named the two private working documents by filename
(`CLAUDE.md`, the SOP transcription) multiple times, including a footnote spelling out
their exact paths. The existing rule only covered README/public docs; the correction
broadened it to the whole repo, ADRs included, since those get committed. Fixed both
drafts to describe the sources generically ("the earlier direction," "NiTISI's operating
SOP") instead, and updated the standing memory to match, since it would have produced the
same mistake again next session otherwise.

### Part 1 — Eight corrections to the schema before writing it

1. **Dropped `sequenceNo` and the generated-column idea for `code`.** The first draft used
   a per-table `autoincrement()` int plus a Postgres *generated* column computed from it.
   Replaced with: one dedicated Postgres `SEQUENCE` per prefix (`prj_code_seq`,
   `tp_code_seq`, `pr_code_seq`), a small SQL function `format_code(prefix, n)`, and a plain
   column `DEFAULT` that calls both. `format_code` pads to *at least* 6 digits without
   truncating — the bug in the very first idea (bare `lpad(n::text, 6, '0')`) is that
   Postgres's `lpad` **truncates** a string already longer than the target width, so a
   7-digit sequence value would have silently lost its leading digit past `999999`.
   `GREATEST(6, length(n::text))` grows the target width with the number instead.
2. **`TechPackVersion.fileUrl` replaced with an `Attachment` table** (many files per
   version: design references plus the tech pack document itself), which needed its own
   short ADR — 0008 — proposing an `AttachmentStorage` interface with a `LocalDiskStorage`
   dev implementation, swappable later, mirroring the reasoning ADR 0001 already gives for
   choosing an ORM partly because it can be swapped.
3. **Added `TechPack.phase`** (copied from `Project.phase` at creation time, not read live —
   so a project's later Proto→Bulk move can't retroactively reclassify an already-approved
   Tech Pack) and **`Project.protoCompletedAt` / `completedAt`**.
4. **Tech Pack void traceability**: `voidedById`, `voidReason`, and `supersedesId` (a
   self-relation from the new Tech Pack back to the one it replaced, `@unique` since a
   voided one has at most one successor).
5. **`onDelete: Restrict`, not `Cascade`, on every new relation** — deliberately stricter
   than the old module, since these tables *are* the approval/traceability trail.
6. **Dropped `ProtoRequest.techPackId`** — derivable via `techPackVersion.techPack`, so a
   second FK that has to agree with the first earned no query.
7. Rewrote ADR 0006's source description per Part 0.
8. **Planned the first service test**, written into the ADR rather than code yet: a Tech
   Pack with `v2` confirmed and `v3` uploaded afterward — a Management approval naming `v3`
   must be rejected, because a check that only asks "does *any* version have a confirmation"
   would wrongly let it through.

`CLAUDE.md`'s role-expansion line was also corrected to match the additive decision from
last session (`MANAGER`/`ENGINEER` kept, new SOP roles added alongside) — edited, not
committed, since the file is gitignored.

### Part 2 — Writing and validating the schema

Added the new enums/models to `schema.prisma` (additive `UserRole` values, 8 new relations
on `User`, and `Project` / `TechPack` / `TechPackVersion` / `Attachment` / `TechPackRemark`

### Part 3 — Running the migration

Docker Desktop wasn't running (needed manually starting first; the Postgres container came
back up on its own once the daemon was ready, waited on its healthcheck).

`prisma migrate dev --create-only --name sop_slice_a`, then hand-edited the generated SQL:
`format_code()` and the three sequences created at the top, before anything references
them; `ALTER SEQUENCE ... OWNED BY "<table>"."code"` added after the `CREATE TABLE`s, so a
`TRUNCATE ... RESTART IDENTITY` in tests resets the counters and dropping a table drops its
sequence with it.

**Applying it surfaced exactly the risk the ADR had flagged and hedged against — a
`dbgenerated()` default is opaque to Prisma's own diffing.** After applying cleanly,
`migrate dev` went interactive, prompting to name a *further* migration, which it shouldn't
have needed to since nothing in `schema.prisma` had changed since generation. Diagnosed
non-interactively (`prisma migrate diff --from-config-datasource --to-schema ... --script`,
then reading the actual stored default straight from `information_schema.columns`):
Postgres normalizes a stored default expression by adding explicit casts —
`format_code('PRJ', nextval('prj_code_seq'))` is stored and read back as
`format_code('PRJ'::text, nextval('prj_code_seq'::regclass))` — and Prisma compares that
normalized form against the literal, uncast string in `schema.prisma`, sees a permanent
textual mismatch, and would propose a no-op "fix" migration forever. Fixed at the source:
updated all three `dbgenerated()` strings in `schema.prisma` to the cast form Postgres
actually stores, confirmed with `migrate diff --exit-code` that the diff was empty
(exit 0), *then* re-ran `migrate dev`, which reported "Already in sync, no schema change or
pending migration was found" — the round-trip check the ADR called for, now clean.
`prisma generate` was run explicitly afterward, since (as in earlier sessions) `migrate dev`
here doesn't reliably regenerate the client on its own.

### Part 4 — Sanity checks in psql

`SELECT format_code('PRJ', 1), format_code('PRJ', 1234567)` → `PRJ-000001`, `PRJ-1234567` —
confirms the non-truncating pad works past 6 digits. Inserted a real `Project` row and
confirmed `code = 'PRJ-000001'`; deleted it afterward (a throwaway sanity check, not real
data) and reset `prj_code_seq` back to 1 so the dev database's first real Project still
gets `PRJ-000001` rather than `PRJ-000002`.

### Things that went wrong (no lasting effect)

- **Docker Desktop wasn't running** at the start of this step; started it and waited on the
  container's healthcheck before running anything against the database.
- **The `dbgenerated()` cast-normalization mismatch**, described in Part 3 — the real

  in the abstract without knowing what form it would take.

  advisory lock.** When `migrate dev` went interactive it was moved to a background task;

  processes and matching the exact command line before killing it — the same
  identify-before-kill discipline used in earlier sessions for stray dev servers, just
  applied to a Prisma process instead.

## Step 14 — Starting Slice A's service layer: authorization finalized, storage service +
Project (Stage 1) built

New branch, `feat/sop-slice-a`, cut from the tip of `feat/full-view-actions` rather than
`main` — `main` turned out to be stale, missing the entire `Approval`/access-control schema
that only exists on the unmerged `feat/full-view-actions` branch, so branching from bare
`main` would have silently dropped already-built functionality from the new branch. A single
`git checkout -b` at the current commit, so nothing needed stashing.

### Part 1 — Finalizing SOP-domain authorization

ADR 0007 had left this as "a plain role gate... not finalized." Finalized it, with one
correction to my proposed default: **`ADMIN` does not bypass Tech Pack confirmation or
approval** — those stay `ENGINEERING`-only and `MANAGEMENT`-only, because they're audit
records of who actually reviewed something, not ordinary data entry, and an always-available
admin bypass would undermine exactly what they exist to prove. Wrote this up as its own ADR
(0009) rather than folding it into 0007, since it's a standalone, citable rule with its own
reasoning and alternatives, not an implementation detail of the coexistence ADR.

Rest of the mapping: PMO creates Projects (ADMIN too — 0009 only narrows the two sign-off
gates, nothing else); Product Designer owns Tech Packs/versions/attachments (ADMIN too);
remarks open to Engineering and Product Designer (ADMIN too); reads open to any authenticated
user for now. A new `requireRole(...roles)` middleware implements this — a plain role check
against the actor's current (DB-fresh) role, deliberately not ADR 0004's assignment/visibility
model, since the SOP states no confidentiality need for who can *see* a Project, only who may
act on one.

### Part 2 — Storage service (ADR 0008), built but not yet wired to an endpoint

`AttachmentStorage` interface + `LocalDiskStorage` implementation, plus the upload policy
(`MAX_ATTACHMENT_SIZE_BYTES` = 25 MB, an extension allowlist: pdf/doc/docx/dwg/dxf/step/stp/
png/jpg/jpeg) as constants callers will enforce before `save()` — not inside the storage
implementation itself, so a future object-storage implementation doesn't have to duplicate
that policy. `storageKey` is always a random UUID (+ sanitized extension), never derived from
the caller's filename, so a malicious original name can't attempt path traversal; `resolvePath`
also refuses to resolve outside the storage root as defence in depth. No upload/download HTTP
endpoint exists yet — that's part of the TechPack step, since attachments belong to
`TechPackVersion`, which doesn't exist as an API yet either.

### Part 3 — Project (Stage 1)

Repository → service → controller → routes, matching the existing layering exactly.
`createProject` takes the authenticated actor's id directly as `createdById` — unlike the old
module's `Product.ownerId`, the SOP doesn't describe creating a Project on someone else's
behalf, so there was no separate id to validate against `users` the way `productService` does
for an arbitrary `ownerId`. Mounted at `/projects`, inside the same `authenticate` gate as
every other route, alongside (not inside) `productRoutes`.

Seed gained one user per new SOP role (`pmo@`, `designer@`, `engineering@`, `management@`,
`merchandiser@kyvera.dev`), re-ran against the dev database, confirmed all nine seeded users
and roles with a direct query.

### Part 4 — Tests, and a bug ADR 0006 predicted in the abstract

`localDiskStorage.test.ts` (9 tests): round-trip, storageKey not derived from the original
name, an unsafe extension sanitized rather than embedded, root directory created on first
save, delete is idempotent, and a storage key trying to escape the root is refused.

`projects.test.ts` (15 tests, route-level via supertest): happy path including the generated
`code` shape; `productCategory` optional; required-field validation; a table-driven 403 test
over every role that is *not* `PMO`/`ADMIN` (`MANAGER`, `ENGINEER`, `FINANCE`,
`PRODUCT_DESIGNER`, `ENGINEERING`, `MANAGEMENT`, `MERCHANDISER` — so a role added later can't
silently gain access, the same reasoning as the old module's table-driven access tests); reads
open to any role; 404 for both an unknown and a malformed id. Added `/projects` and
`POST /projects` to `auth.test.ts`'s existing table-driven "every route requires a token" test
rather than duplicating that coverage here.

**The first test run failed** — not the code under test, the test file's own cleanup order.
`afterAll` called `cleanupTestUsers()` without first deleting the Projects those test users had
created, and `Project.createdBy` is `onDelete: Restrict` (ADR 0006, point 9, deliberately
stricter than the old module), so deleting a user who created a Project is refused at the
database level. This is exactly the "more ceremony than the old module's tests" consequence
ADR 0006 named in the abstract, now met concretely. Fixed by following the same pattern
`access.test.ts` already uses for `Product`: track created ids, delete them before
`cleanupTestUsers()`. The failed run's own leftovers (4 orphaned Projects and their 16
`@kyvera.test` creator users, never cleaned up because the first `deleteMany` had already
failed and rolled back) were found and deleted by hand afterward, and `prj_code_seq` reset back
to 1 so the dev database's numbering stays clean.

**228 tests passing** (201 old + 27 new) after the fix.
