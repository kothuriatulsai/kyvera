## Step 18 — SOP Slice A: TechPackApproval (Stage 3, Management half) + ProtoRequest

Continuing `feat/sop-slice-a`. Last backend step of Slice A - schema already existed; this
was service/API layer, same pacing as Stages 2 and 3's Engineering half.

### Part 1 — Repositories, service, controllers, routes

`techPackApprovalRepository` (`create`), `protoRequestRepository` (`findMany`/`findById`/
`create`, all with `project` and `techPackVersion.techPack` nested so a ProtoRequest's
response shows exactly "which project, which Tech Pack, which version" without a second
round trip). Added `techPackRepository.voidTechPack` - sets `voidedAt`/`voidedBy`/`voidReason`
on a rejection, the counterpart to `create`.

New `techPackDecisionService.decideTechPackVersion` is the last piece of Stage 3: Management's
`APPROVED`/`REJECTED` call on a confirmed, latest `TechPackVersion`. Runs the whole check
sequence inside one transaction behind `techPackRepository.lockById` - the same row lock
`uploadTechPackVersion` and `confirmTechPackVersion` already take, so a decision can't race a
concurrent upload or another decision on the same TechPack. In order: 404 if the TechPack or
version is missing, 409 if voided or if any version is already approved, 409 if
`versionNumber` isn't the latest version, 409 if the latest version has no `TechPackConfirmation`
- this is the exact case ADR 0006 planned a test for when it first wrote the rule ("a version
is confirmed, a newer unconfirmed version is uploaded afterward - approving the newer one must
check *that version's* confirmation, not just whether *some* version has one"). `notes` is
validated as required before any of that, when rejecting - a day-zero check, no need to open
a transaction first to reject a request missing it.

**Approve**: creates the `TechPackApproval` row, then a `ProtoRequest` pinned to this exact
`TechPackVersion` (`code` generated the same `format_code()`-backed way as `Project`/`TechPack`).
Returns `{ decision: "APPROVED", techPack, protoRequest }`.

**Reject**: creates the `TechPackApproval` row (decision `REJECTED`, `notes` carried over),
voids the TechPack (`voidTechPack`), then creates a *new* `TechPack` under the same
Project/phase with `supersedes` pointing at the voided one - no versions of its own yet.
Returns `{ decision: "REJECTED", techPack: <the new one>, protoRequest: null }`. This new
TechPack needed no special-casing anywhere else: `uploadTechPackVersion`'s `nextVersionNumber`
already falls back to `1` when `findLatestByTechPack` finds nothing, and
`findActiveByProjectAndPhase` already counts any non-voided TechPack regardless of how many
versions it has - both were already correct for a zero-version TechPack without this step
touching either function.

The whole transaction is wrapped in the same `P2002`→409 defence-in-depth pattern
`confirmTechPackVersion` already uses, for `TechPackApproval.techPackVersionId`'s unique
constraint.

New route: `POST /tech-packs/:id/versions/:versionNumber/decision`, `MANAGEMENT`-only, no
`ADMIN` carve-out (ADR 0009) - the third and strictest of this domain's role gates. New
`protoRequestRoutes` (`GET /proto-requests`, `GET /proto-requests/:id`), reads open to any
authenticated user like the rest of the domain; no write endpoint, since a ProtoRequest is
only ever created as a side effect of an approval.

### Part 2 — Tests

`techPackDecision.test.ts` (21 tests): approve happy path (ProtoRequest's code/shape, pinned
project + Tech Pack code + version number); reject happy path (successor's `supersedes`,
zero versions, the voided original's `voidReason`/`voidedBy`/`supersededBy`, the voided
original refusing both a further upload and a further remark, the successor accepting v1,
and the successor now correctly counting as the Project's one active TechPack so a fresh
`createTechPack` on it 409s); notes required on reject, not required on approve; a
table-driven 403 over every non-`MANAGEMENT` role **including `ADMIN`**; 404 for an unknown
TechPack id and version number; 409 voided, 409 already-approved, 409 not-latest; the ADR
0006 "v2 confirmed, v3 uploaded" case built exactly as planned (confirm v2, upload v3,
approve-attempt on v3 → 409, because v3 itself has no confirmation even though v2 does); and
a `Promise.allSettled` race between an approve and a concurrent version upload, asserting
exactly one success and - whichever one wins - never an approval that ends up targeting a
version that quietly stopped being the latest underneath it. `GET /proto-requests` tests:
list/get round-tripping the nested project/Tech-Pack-code/version shape, and a 404 for an
unknown id. Added the three new routes to `auth.test.ts`'s token table.

Every test in this file passed on the first run, including the concurrency one - the same
row lock already proven out by Step 17's concurrent-confirm test carries over directly, so
there was no flaky-then-fixed story to tell this time.

## Step 19 — Chore: give the API's tests their own database and uploads directory

Before the Slice A frontend pass: paid down the follow-up chore from Step 15 (the dev-DB
pollution incident - tests running against the same `DATABASE_URL` as dev, confirmed to have
actually bitten once already). Entirely test-infrastructure; no application code changed.

### Part 1 — The test database

`tests/testEnv.ts` (new, shared between the two files below): `resolveTestDatabaseUrl()`
reads `TEST_DATABASE_URL` (default `postgresql://kyvera:kyvera@localhost:5432/kyvera_test?schema=public`)
and **throws if the database name doesn't end in `_test`** - the safety guard, checked before
any connection is opened, not just before the truncate it's protecting. Also exports
`TEST_UPLOADS_DIR`, a *fixed* path under `os.tmpdir()` rather than a fresh `mkdtemp()` per run
- explained below.

`tests/globalSetup.ts` (new): Vitest's `globalSetup` runs this once, in the main process,
before any test file. In order: connects to the `postgres` maintenance database and creates
`kyvera_test` if `pg_database` doesn't already have it; shells out to `npx prisma migrate
deploy` with `DATABASE_URL` overridden to the test URL for that one subprocess (so
`prisma.config.ts`'s own `dotenv` call, which never overrides an already-set variable, picks
up the test URL instead of `.env`'s dev one); opens a one-off `PrismaClient` against the test
database to `TRUNCATE` every `public` table except `_prisma_migrations` with `RESTART IDENTITY
CASCADE` (table list read dynamically from `pg_tables`, not hardcoded, so a table a later
slice adds is covered with no change here) and reseed `stage_definitions`; and resets the
uploads temp directory. `RESTART IDENTITY` is also what resets `prj_code_seq`/`tp_code_seq`/
`pr_code_seq` back to 1 on every run - they were already set up to be `OWNED BY` their table's
`code` column for exactly this (Step 15's journal entry, written before any of this existed,
already named this as the reason). Extracted the nine-row `stages` array out of `seed.ts` into
`src/prisma/stageDefinitionSeedData.ts` so the dev seed and this minimal test seed share one
source of truth instead of two copies that could drift.

`tests/setup.ts` (per-worker, existing `setupFiles` entry) now also sets `process.env.DATABASE_URL`/
`UPLOADS_DIR` from the same `testEnv.ts` resolver, directly in each worker process, rather than
relying solely on `globalSetup` mutating `process.env` in the *main* process and hoping that
mutation reaches already-spawned worker threads/forks - Node gives a worker a snapshot of its
parent's env at creation time, and there's no documented guarantee that snapshot happens after
a `globalSetup` mutation rather than before it. Both `globalSetup` and `setup.ts` still set
these (belt-and-suspenders), but `setup.ts`'s own assignment is what's actually relied on.

**Why `TEST_UPLOADS_DIR` is a fixed path, not `mkdtemp()`:** a random temp directory generated
once by `globalSetup` would need to reach every worker process the same way `DATABASE_URL`
does - and for the same reason just described, that hand-off can't be trusted. A fixed,
well-known path means every worker independently resolves the *same* directory with zero
coordination; `globalSetup` just removes and recreates it fresh on each run.

### Part 2 — Wiring and CI

`vitest.config.ts` gained `globalSetup: ["./tests/globalSetup.ts"]` alongside the existing
