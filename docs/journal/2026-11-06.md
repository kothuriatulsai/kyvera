# 2026-11-06

## Step 29 — Manufacturer master, Proto Request Stage 4, Proto Work Stage 5 (ADR 0015)

Slice B: the SOP's Stage 4 (assign a manufacturer, Finance uploads the PO, PMO confirms) and
Stage 5 (the confirmed request becomes a `ProtoWork`, PMO assigns a Merchandiser, who tracks
progress, reconfirms the delivery date periodically, then marks it complete). Planned in a
checkpointed pass (schema -> repositories -> services -> controllers/routes -> tests, reviewing
the diff after each phase) before any code, then built API-first with tests; the web UI is not
started yet. Full design and rationale in ADR 0015.

### What got built

- **Schema**: `ManufacturerMaster` (master data, no `code` - the SOP's own ID table doesn't list
  one for it); `ProtoRequest` gained Stage 4's fields (manufacturer assignment, commercial notes,
  a PO via a new `Attachment.protoRequestId` owner column - exactly what ADR 0008's own comment
  predicted, agreed delivery date, confirmation); `ProtoWork` (code `PW-`, new `pw_code_seq`
  alongside the existing `format_code()`), `ProtoWorkDeliveryConfirmation` (append-only history
  paired with `ProtoWork.currentDeliveryDate`), `ProtoWorkUpdate` (the step-21 chat thread, same
  shape as `TechPackRemark`). Five new `NotificationType` values.
- **API**: `manufacturerService`/`protoWorkService` (new), `protoRequestService` extended with
  `assignManufacturer`/`uploadPo`/`confirmProtoRequest`, `visibility.ts` extended
  (`assertProtoRequestPoVisible` - layer A only, mirroring `ProtoRequest`'s own rule),
  `notificationService` (5 new `notify*` helpers), `taskService` (PMO gains three contributions;
  FINANCE and MERCHANDISER get their first tasks ever). New `/manufacturers` and `/proto-work`
  routers; `/proto-requests` gains the three Stage 4 actions.
- **Tests**: `manufacturers.test.ts`, `protoWork.test.ts` (68 tests, the full Stage 4->5 chain),
  extensions to `myTasks.test.ts`, `notifications.test.ts`, `visibility.test.ts`. A new
  `tests/helpers/cleanup.ts` centralizes the FK-respecting teardown - the chain now runs
  TechPack -> ProtoRequest -> ProtoWork -> its own children, deep enough that copy-pasting it into
  a sixth file risked getting the order wrong in one copy (ADR 0006's `onDelete: Restrict`
  everywhere means teardown order is never optional).

### Judgment calls made while building (flagged in ADR 0015, not silently decided)

1. **ADMIN is a carve-in on every new gate**, not a carve-out - none of Slice B's actions are the
   kind of two-party adjudication ADR 0009 carved ADMIN out of (Engineering confirm / Management
   decide); they're single-party operational actions like "PMO creates a Project," which already
   includes ADMIN.
2. **No notification on a routine delivery-date reconfirmation** - it only resets the reconfirming
   Merchandiser's own task clock, same reasoning ADR 0014 already used for version-upload noise.
3. **`DELIVERY_RECONFIRMATION_INTERVAL_DAYS = 7`** - the SOP says "regular intervals" with no
   number; kept as one named constant in `taskService.ts` rather than guessed-and-buried.
4. **ENGINEERING gets no new Stage 5 task** - named a process owner in the SOP's role table, but
   no concrete system action is described for them there, unlike Stage 3's explicit steps.
5. **No access-control meaning to `ProtoWork.assignedMerchandiserId`** beyond the assign action
   itself - any MERCHANDISER project member may reconfirm/update/complete, matching the precedent
   Tech Pack confirmation already set (not restricted to a specific assigned Engineer either).

### A test bug caught before it shipped

The first draft of the "confirming notifies every other active PMO" test asserted on
`notifications[0]`, assuming the Proto Request's own `PROTO_WORK_QUEUED` event would be that PMO's
only notification. It wasn't - that same PMO was also a recipient of the *earlier*
`TECH_PACK_VERSION_APPROVED` fan-out from approving the Tech Pack in the test's own setup (PMO is a
recipient of that event too, per ADR 0014). Fixed by filtering on `type` before asserting, the same
lesson `techPackDecision.test.ts` already encodes elsewhere in this codebase - a see-all role's
notification list is never purely about the one event a test thinks it's isolating.
