## Step 15 — SOP Slice A: TechPack + TechPackVersion + Attachment upload/download (Stage 2)

Continuing `feat/sop-slice-a`. Schema for this step already existed (ADR 0006/0008); this
was entirely service/API layer, following the Project (Stage 1) layering exactly.

### Part 1 — Repositories, service, controllers, routes

`techPackRepository` (list/get with nested versions → attachments/remarks/confirmation/
approval, `findActiveByProjectAndPhase`, and `lockById` — a raw `SELECT ... FOR UPDATE`
since Prisma has no typed row-lock primitive), `techPackVersionRepository`
(`findLatestByTechPack`, `hasApprovedVersion`), `attachmentRepository` (`create`/`findById`).

`techPackService.createTechPack` validates the file list (at least one, each within the
existing allowlist/size policy — defence in depth behind the upload middleware), then, inside
a transaction, locks the Project row and checks "at most one non-voided TechPack per Project
per phase" before creating TechPack + TechPackVersion(1) + Attachments. `uploadTechPackVersion`
locks the TechPack row first, rejects a voided TechPack or one with any approved version, then
creates version N+1 the same way. (The first version of this lock on `createTechPack` was
missing — see Step 16.)

No multipart parser existed yet (`express.json()` only handles JSON bodies). Added
`multer` + `@types/multer` (hoisted to the repo-root `node_modules` by the npm workspace) and
wrote `attachmentUpload`, a small wrapper middleware around `multer({ storage:
memoryStorage(), limits, fileFilter })`: `fileFilter` rejects a disallowed extension as a
`ValidationError` before Multer buffers the file at all, and the wrapper converts a
`MulterError` (oversized file, too many files) into the same `ValidationError` shape — so a
bad upload reaches the client as a normal 400, not Multer's own error format or the generic
500 handler. Kept entirely inside this one file; `app.ts` stays unaware Multer exists.

Attachment downloads are their own router, `GET /attachments/:id/download` — deliberately
not nested under `/tech-packs`, since ADR 0008 expects `Attachment` to gain more nullable
owner FKs later (a PO in Slice B); a flat, id-only download endpoint outlives any one owner.
Sets `Content-Type` from the stored MIME type and a `Content-Disposition` built from the
stored original filename — both forms (`filename="..."` and `filename*=UTF-8''...`), the
ASCII fallback stripped to printable characters first so neither form can inject an extra
header line or parameter from a crafted original filename.

Role gates follow the mapping finalized in the previous session's journal entry: Product
Designer owns Tech Pack creation and version upload (ADMIN too — ADR 0009 only narrows the
Engineering-confirm/Management-approve gates, neither of which exists yet); reads (including
downloads) stay open to any authenticated user.

### Things that went wrong (no lasting effect on the code, but did leak dev data)

**The test file's `afterAll` had the same shape of bug the previous session hit for
`Project`, one level deeper.** First version's cleanup order was `Attachment` →
`TechPackVersion` → `TechPack` → `Project` → users — but one test (exercising "refuses a new
version once a version has been approved") inserts a `TechPackApproval` row directly, and
that FK (`onDelete: Restrict`, ADR 0006 point 9) blocked the `TechPackVersion` delete. Fixed
by deleting `TechPackApproval` rows for the run's TechPacks before deleting their versions —
analogous to deleting `Project`s before their creator users.

**Because the first (failing) run's `afterAll` threw before reaching any of its deletes past
the failure point, none of that run's Projects/TechPacks/versions/users were cleaned up** —
and since tests run against the same dev database (`DATABASE_URL`), not an isolated test DB,
that run's ~27 Projects, 19 TechPacks, 20 versions and 64 `@kyvera.test` users sat in the dev
database until found and deleted by hand (scoped by `createdById`/email, confirmed empty
afterward, confirmed zero old-module rows referenced those users before deleting). Recorded
as a standing follow-up chore in `CLAUDE.md`: give tests their own database, reset with
`TRUNCATE ... RESTART IDENTITY` before each run, so this class of bug can leak at most within
a throwaway test database, never into dev data again.

`prj_code_seq` and `tp_code_seq` are left past 1 after this cleanup (the sandbox's auto-mode
classifier refused a direct `ALTER SEQUENCE ... RESTART`, unlike the plain `DELETE`s moments
earlier) — purely cosmetic, the next real Project/TechPack simply won't start at `-000001`.
Flagged to the user rather than worked around; they chose to leave it and asked for the test-DB
isolation chore above instead of a one-off fix.

## Step 16 — Pre-commit review fixes on Stage 2

Review of Step 15 before committing it found two correctness issues and a small hardening
gap, all in `techPackService.ts` / `contentDisposition.ts`. Fixed all three before anything
from Step 15 was committed.

### Fix 1 — `createTechPack`'s active-TechPack check had no lock

The "at most one non-voided TechPack per Project per phase" check ran as a plain read before
the transaction, with nothing serializing it against a second concurrent call doing the same
read. Two requests creating a TechPack for the same Project and phase at the same time could
both see "no active TechPack yet" and both proceed — the exact TOCTOU race the step's own
comment had explicitly called out and left unaddressed.

Fixed by moving the check inside the transaction, after taking a row lock on the *Project*
(`projectRepository.lockById`, a new function — same `SELECT ... FOR UPDATE` + typed
`findUnique` pattern as `techPackRepository.lockById`). A concurrent create for the same
Project now serializes on that lock: the second transaction blocks until the first commits,
then re-reads and correctly finds the TechPack the first one just created, so it fails the
check instead of racing past it. The `createTechPack` comment claiming this race was
out of scope was wrong to begin with and is removed.

Added a test that fires two creates concurrently via `Promise.allSettled` and asserts exactly
one `201` and one `409` — this is the test that would have been flaky/both-201 before the fix
and is deterministic after it, since Postgres now serializes the two transactions rather than
letting them interleave.

### Fix 2 — attachment bytes were written to storage inside the transaction

`saveAttachments` called `attachmentStorage.save()` (disk I/O) from inside the Prisma
interactive transaction, for every file, before writing that file's `Attachment` row. Two
problems: Prisma's interactive-transaction timeout defaults to 5 seconds, sized for database
work, not for however long writing one or several files takes, so a large or multi-file
upload could trip that timeout and abort a transaction that had otherwise done nothing wrong;
and when the transaction then rolled back (whether from that timeout or any other failure
after a file had already been saved), the already-written file was never cleaned up — an
orphan on disk with no `Attachment` row ever pointing at it.

Restructured both `createTechPack` and `uploadTechPackVersion` around the same shape:
`saveFilesToStorage()` runs *before* the transaction and returns the saved files' storage
keys and metadata; the transaction itself only ever does database writes (`createAttachmentRows`
connects the already-saved keys to new `Attachment` rows); and a `try/catch` around the
transaction calls `deleteSavedFiles()` — a best-effort, `Promise.allSettled`-based cleanup
that swallows its own failures so it can't hide the original error — on any failure, then
rethrows. `saveFilesToStorage` itself is wrapped the same way, so a failure partway through
saving several files cleans up the ones that did succeed before propagating.

Added a test: void a TechPack, snapshot `apps/api/uploads/`'s contents, attempt a two-file
version upload against it (expected 409 — voided), and assert the directory's contents are
unchanged. Without Fix 2 this would have left two new files behind.

### Small fix — `Content-Disposition`'s ASCII fallback

`attachmentContentDisposition`'s ASCII-fallback branch replaced non-printable characters and
double quotes but not backslashes, which also have syntactic meaning inside an HTTP
quoted-string (`\"` is an escaped quote, so an unescaped `\` right before the closing `"`
could change where a naive parser thinks the filename ends). Added a third `.replace(/\\/g,
"_")` pass alongside the existing non-printable and quote replacements.
