## Step 7 — Accept ADR 0004, and fix the PATCH status footgun

### Part 1 — ADR 0004 accepted (docs only)

`docs/architecture/0004-stage-level-access-control.md` moves from Proposed to
Accepted, with all five open questions resolved. No code was touched.

The five decisions, in short:

1. **Visibility** — an assignee sees only their own assigned stages plus a
   server-derived readiness hint ("up next" / "opens in ~N days" / "open now" /
   "completed"); no other stage names or statuses.
2. **Progress vs. transition** — two separate actions. Recording a delay
   reason/status note on your own stage is open to any assignee at any time and
   never moves the product. Advancing is guarded: sole assignee finishing their
   stage can trigger it; with several assignees each sets a `ready_at` on their
   assignment row; admin/manager can force it. Backward moves stay
   admin/manager-only.
3. **Roles vs. assignment** — role gates which kinds of actions/modules you can
   use (e.g. `FINANCE` for Module 3's budgets); assignment gates visibility into
   a product's stage data. Role alone grants no product visibility.
4. **Owner** — full visibility of their own product only ("local admin" for it).
5. **Outside contributors** — ordinary `users` rows with no assignments until
   an admin adds some; no separate account type.

What the rewrite involved beyond flipping the status line:

- The Decision section had to change, not just the questions section. The old
  text said an assignee could record progress only on a stage "the product is
  currently in"; Resolution 2 says "at any time," so that wording was wrong once
  the question was resolved. Also added the `ready_at` column to the
  `product_stage_assignments` sketch and the owner projection.
- The old "Open questions" section became a "Resolution notes" subsection
  (reasoning for each answer, in prose), and the Alternatives section now also
  records the rejected options for Q1(b), Q2 and Q5. The "per-product membership"
  alternative is still rejected for assignees but is now noted as adopted,
  narrowly, for owners.
- A stale line in the Consequences section still described the frontend's
  per-product `/delay` calls, which were removed in step 6; corrected.
- `0005-approval-records.md`: replaced the "revisit when 0004 is accepted"
  bullet with a pointer to 0004's Resolution 2 — the approval gate's
  `ADMIN`/`MANAGER` authority is meant to match "admin/manager can force a
  transition" once real authentication exists. It still says plainly that plain
  backward/forced transitions are not role-gated in the API today.

**Things the resolutions leave open** (written into the ADR as "Points these
resolutions leave for implementation", not decided by me):

- A manager can force/backward-transition, but role alone gives no visibility.
  How can a manager act on a product they can't see? Working assumption in the
  ADR: authority applies to products they own or are assigned to; admin covers
  the rest. Needs confirming.
- Whether an owner's "local admin" status lets them approve or force-transition
  their *own* product — a separation-of-duties question against ADR 0005, which
  restricts approvals to `ADMIN`/`MANAGER`.
- Who triggers the transition once every assignee of a multi-assignee stage is
  ready.
- Where progress notes are stored relative to `ProductStageHistory.delay_reason`.

Dating: the ADR's "Accepted" date and this journal are dated 2026-09-20, the day
these are being committed, rather than the day the text was written.

### Part 2 — PATCH /products/:id status footgun

`PATCH` accepted `status: "DELAYED"` / `"ON_TRACK"` and returned 200 with the
new value, but since step 6 reads compute status from delay, so the write had no
lasting effect — a silent no-op that looked like it worked. Now
`productService.updateProduct` rejects it with a `400`: "status is derived from
delay computation; only BLOCKED can be set manually". The check lives in the
service (a business rule), before any write, so a rejected request applies none
of its other fields either (there's a test for that).

**One deliberate deviation from "reject DELAYED/ON_TRACK".** `BLOCKED` always
wins over the derived value, so the only way to *clear* a block was previously a
`PATCH` with `ON_TRACK`/`DELAYED`. Rejecting both outright would have left any
blocked product blocked forever. So `ON_TRACK` is still accepted — but only on a
product that is currently `BLOCKED`, where it means "clear the block". The value
stored is then whatever the delay computation says (`ON_TRACK` *or* `DELAYED`),
never the raw value sent; an overrun product cleared this way comes back
`DELAYED` (tested). `DELAYED` is always rejected. If a different unblock
mechanism is preferred later (say, an explicit `blocked` flag or an
`/unblock` action), this is the one branch to replace.

- **Tests:** replaced the old "updates product status" test (which asserted the
  footgun) with: DELAYED → 400 with the message; ON_TRACK on an unblocked
  product → 400; BLOCKED accepted; DELAYED rejected on a blocked product and
  ON_TRACK clears it and re-derives; other fields still apply alongside a valid
  status; nothing applies when the status is rejected. Plus one in
  `liveStatus.test.ts` for the overrun-then-unblocked case. Confirmed these fail
  with the guard removed (4 do).
- **shared-types:** no change — there's no request type for `PATCH` fields in the
  package, so no shape to update. Worth adding one when the frontend gets write
  flows.
- README: the `PATCH` row now describes the rule.

**A bug in my own earlier work, found and fixed along the way.** The first
attempt at this edit failed with a `UnicodeDecodeError`: `productService.ts`
contained a lone `0x97` byte. Cause: last session's Python edit scripts opened
files without an explicit encoding, so on Windows they were read/written as
cp1252, and where the *replacement text* contained an em dash it was written as
a single cp1252 byte instead of UTF-8. Scanned every tracked file: exactly two
were affected, both mine and both already committed on the branch —
`apps/api/src/services/productService.ts` and
`packages/shared-types/src/index.ts`, one comment line each (they'd have
compiled, showing a replacement character in the comment). Fixed at the byte
level; no other file was affected, and no mojibake (`â€”`) anywhere. Lesson: pass
`encoding='utf-8'` explicitly when scripting file edits on Windows.

## Step 7, continued — the four remaining ADR 0004 points, then committing

### Part 1 — ADR 0004 follow-up resolutions (docs only)

The four points the acceptance left open are now settled in
`docs/architecture/0004-stage-level-access-control.md` (a "Follow-up
resolutions" subsection, numbered 6–9 after the original five), and the ADR's
Status line now says all of them are resolved. No code changed.

6. **Manager authority is scoped to visibility.** A manager can force a
   multi-assignee transition or go backward only on products they own or are
   assigned to; only an admin is unscoped. Chosen over blind manager authority so
   a second access model doesn't grow beside the visibility one.
7. **Owner's local-admin status extends to approvals** on their own product
   (approval gate = admin, the product's owner, or an assigned manager).
   Consequence written into the ADR: an owner can approve their own product — no
   separation of duties, a conscious trade-off.
8. **A fully signed-off multi-assignee transition needs a manual trigger** — not
   an auto-fire on the last `ready_at`, which would attribute the transition to
   whoever happened to sign off last when nobody decided to advance the product.
9. **Progress notes get their own table**, `stage_progress_notes` (`id`,
   `product_id`, `stage_id`, `user_id`, `note`, `created_at`), rather than reusing
   the deferred `comments` table; they're scoped functional data read by the
   readiness/delay views, so this doesn't reopen the `comments` deferral in
   ADR 0005.

Beyond appending the four items, the rest of the ADR had to be brought in line
so it doesn't contradict itself: Decision item 4 previously said "admin or
manager can force it" and "the transition proceeds once all are ready", both
superseded; Resolution 2's wording, the Consequences and the Alternatives
(three new rejected options) were updated too. I introduced one term to keep the
rules from being restated four times: **"authority over a product"** = admin
(unscoped) ∪ the product's owner ∪ a manager assigned to it. Forcing, backward
moves, triggering a signed-off transition and approval decisions all use that
one set.

**One inference of mine to confirm.** Resolutions 6 and 8 as given name only
"admin, or the owning/assigned manager". I included the *owner* (whatever their
role) in that set for forcing/backward/triggering as well, because Resolution 4
makes the owner a local admin and Resolution 7 already puts them in the approval
gate — otherwise the owner could approve a product but not advance it, which
seemed unintended. If owners should *not* be able to force or reverse
transitions, that's a one-line change in the ADR's "authority over a product"
definition.

`0005-approval-records.md`: the "Who can decide" paragraph now states the target
rule ("admin, the product's owner, or an assigned manager"), and says plainly
that the current implementation is coarser — any `ADMIN`/`MANAGER` user for any
product — until authentication and assignment data exist, with the practical
effect spelled out (an owner who isn't a manager/admin gets 403 today; an
unrelated manager is allowed). The Consequences bullet was updated and an
"owner can approve their own product" bullet added.

## Step 8 — Authentication (mechanics only)

Scope: make "who is calling" a real, verifiable thing. Nothing enforces anything
with it yet — no role, ownership or assignment logic (that is ADR 0004's
implementation, next session). Started on a fresh branch, `feat/authentication`,
off the merged `origin/main` (PR #2 had merged).

### Part 1 — Password handling and auth endpoints

- **argon2id, not bcrypt.** It is OWASP's current first choice (memory-hard, so
  GPU cracking is costly), has no 72-byte input limit, and the `argon2` package
  installed and ran cleanly on Windows here and ships prebuilt binaries for
  Linux (glibc and musl), so CI and the alpine Docker image shouldn't need a
  compiler. Default parameters (`m=65536,t=3,p=4`) cost ~80 ms per hash. I
  weighed `bcryptjs` (pure JS, zero install risk) and rejected it as the weaker
  algorithm for no real gain, and `@node-rs/argon2` because its per-platform
  optional dependencies are prone to lockfile problems when the lock is
  generated on Windows and consumed on Linux.
- **The seed really did store a plain-text placeholder**
  (`"unset-no-auth-module-yet"`) in `password_hash` — confirmed in the dev DB
  before reseeding, all four seeded users. The seed now hashes a dev password
  (`kyvera-dev-password`, override with `SEED_USER_PASSWORD`) and replaces only
  values that aren't already an argon2 hash, so a re-seed doesn't reset a
  password someone deliberately changed (verified idempotent by comparing a hash
  of the column before and after a second run). No schema migration was needed —
  it's the same `String` column. Login also treats any stored non-hash as a
  failed login rather than letting argon2 throw into a 500 (tested).
- **Register is public but can never mint a privileged role.** A public endpoint
  accepting `role` would let anyone create an ADMIN, a real hole even before any
  authorization exists. So registration always creates `ENGINEER` (the
  least-privileged role here), and a `role` in the body is a `400` rather than
  silently ignored (the same lesson as the PATCH status footgun). Granting a role
  is admin user-management, per ADR 0004, and is next session. This is my call —
  say if you would rather registration be login-only from the start.
- **One user-creation path.** There was no existing user-creation logic to reuse
  (tests and the seed wrote rows with Prisma directly), so `userService.createUser`
  is the reusable piece: it normalises the email (trim + lowercase), validates it,
  enforces the password policy (8–128 chars), hashes, and turns a unique-violation
  race into a `409`. It takes the role as a parameter — the *caller* decides —
  which is what an admin-only "create user" endpoint will call later.
- **Login** returns `{ token, tokenType, expiresIn, user }`. Wrong password and
  unknown email give the identical `401` body, and an unknown email still burns a
  dummy argon2 verification so response time doesn't reveal which emails exist.
- **Token claims are only `sub` (user id) and `role`** (plus `iat`/`exp`); a
  test asserts the exact claim set so assignment or ownership data can't creep in
  and go stale. HS256 with the algorithm pinned on both sign and verify; a
  correctly signed token is still rejected if `sub` is missing or `role` isn't a
  known role.
- **Expiry / refresh: 1-hour access token, no refresh flow.** Configurable via
  `JWT_EXPIRES_IN_SECONDS`. A refresh-token system means server-side token
  storage, rotation and revocation — real design work, not trivial, and there is
  no client that needs it yet (the web app has no login at all). **Deferred
  follow-up:** refresh tokens (or another way to avoid a hard re-login) when the
  frontend gets a login flow; also login rate-limiting / lockout, which is absent.
- Added `GET /auth/me`, which wasn't asked for: without at least one handler that
  reads `req.actor`, nothing could show the middleware attached the verified actor.
  It returns the caller's own record (401 if the user was deleted since the token
  was issued).

### Part 2 — Verification middleware

- `authenticate` (in `src/middleware/`) verifies the bearer token and sets
  `req.actor = { id, role }`; that's all it does. It is mounted once in
  `routes/index.ts` in front of every existing router, so `/products/*` and
  `/stages` all return `401` without a valid token; `/health`, `POST
  /auth/register` and `POST /auth/login` stay public. Because it sits at the router
  level, an *unknown* path also returns `401` to an unauthenticated caller rather
  than `404`, so route existence isn't revealed. 401s carry `WWW-Authenticate:
  Bearer`. A table-driven test asserts every existing route returns 401 with no
  token, so a route added later can't be left open by accident.
- **Decision: leave `ownerId` / `responsibleUserId` / `decidedById` /
  `createdById` as explicit body fields for now; derive nothing from `req.actor`.**
  The brief said no route's behaviour should change this session, and beyond that
  I judged it the option least likely to need rework. `decidedById` looks
  unambiguous (it should become the actor), but it is not a standalone change: the
  same edit has to make the approval gate check the *actor* against ADR 0004's
  authority set (admin, owner, assigned manager), which needs ownership/assignment
  data that doesn't exist yet. Doing half of that now would change the API contract
  twice and leave an in-between state. `ownerId` and `responsibleUserId` are
  genuinely ambiguous — an admin may legitimately create a product for someone
  else. So next session changes `decidedById` (and how the authority check gets
  its identity) in one place, with the tests.
- **Stateless token, so identity is only as fresh as the token.** The middleware
  does not hit the database, so a deleted user's token still verifies until it
  expires (`/auth/me` catches that case; other routes don't), and a role that
  changes stays stale in the token for up to an hour. That is acceptable while
  nothing authorizes on it, but it needs a decision when roles are enforced next
  session: a per-request user lookup, or a short enough expiry. Recorded rather
  than fixed.

### Part 3 — Tests and secrets

- **New suites:** `auth.test.ts` (register: success, hash stored not password,
  role rejected, case-insensitive duplicate, validation; login: claims, case-
  insensitive email, bad password vs unknown email identical, legacy non-hash,

  expired/`alg: none`/unknown-role/no-subject tokens; `/auth/me`) and
  `config.test.ts` (missing/short/valid secret, lifetime parsing).
- **Existing suites** send a valid token through a small `authedAgent` helper.
  It mints a token directly for a random user id (nothing authorizes on identity
  yet, and the middleware doesn't look the user up); when ADR 0004 enforcement
  lands, these should mint tokens for real users with real roles/ownership.
- **Sanity checks that the tests can fail:** removing the `authenticate` line
  fails 17 tests; removing the role-claim validation fails the targeted test.
  Also ran the tests with no `JWT_SECRET` and got an immediate, actionable
  failure (so nothing is silently defaulting a secret).
- **Secrets.** `JWT_SECRET` is read from the environment, required, at least 32
  characters, and validated on server boot (`assertAuthConfig`) so a
  misconfiguration fails at startup rather than on the first login. It's documented
  in `apps/api/.env.example` (with how to generate one); `ci.yml` sets a throwaway
  value at the job level, the same pattern as `DATABASE_URL`; `docker-compose.yml`
  gives the API a clearly-labelled dev-only default so `docker compose up` still
  works. I also added a generated secret to *your local, gitignored*
  `apps/api/.env` so the dev server and tests keep running — it is not committed.
- **shared-types:** `AuthActor`, `AccessTokenClaims`, `RegisterRequest`,
  `LoginRequest`, `LoginResponse`.
- Extracted the request-parsing helpers (`requireString` etc.) out of
  `productController` into `controllers/requestParsing.ts` so the auth controller
  reuses them instead of copying them.

## Step 9 — Stage-level access control (ADR 0004, implemented)

Builds the data model and the projection/authority logic from ADR 0004 and its
four follow-up resolutions, and wires it into every existing read and write path.
Branch `feat/stage-level-access-control`, off the merged `origin/main`. Not
started, as instructed: the frontend login flow.

### Part 1 - Schema

- Three new tables, all additive: `product_stage_assignments` (unique on
  product + stage + user, indexed on user), `product_stage_assignment_history`
  (append-only; deliberately *not* a foreign key to the assignment row, since that
  row is deleted on unassign and the audit trail must survive it) and
  `stage_progress_notes` (its own table, per Resolution 9, not the deferred
  `comments`).
- **Two columns the brief didn't list, added to `product_stage_history`:**
  `exited_by` and `forced_exit`. Resolution 8 rests on the transition's "caused
  by" audit field, but no such field existed - `responsible_user_id` is the
  body-supplied "who owns this stage", not "who pressed the button". Without
  `exited_by` there is nothing to attribute a transition to, and without
  `forced_exit` a bypassed sign-off is invisible in the audit trail.
- **No seed change was needed.** Existing suites create their own users and
  products, and the seed doesn't create products, so there was nothing for the
  seed to assign; assignments only make sense on a specific product. (`db:seed`
  still gives the four seeded users real password hashes from last session.)
- `prisma migrate dev` applied the migration but, as last time, didn't regenerate
  the client; `prisma generate` had to be run before typecheck saw the new models.
  `prisma format` also realigned some existing lines in `schema.prisma`, so that
  file's diff is noisier than the change (whitespace only).

### Part 2 - Visibility projection

- **One place decides who someone is to a product** (`accessService`): admin, else
  owner, else (assigned *and* role `MANAGER`) manager, else (assigned) assignee,
  else none. Visibility and authority are the same boundary, so `full` is both
  "sees everything" and "holds authority". The same rule exists as a query
  (`visibleProductsWhere`) so a product with no relationship to the viewer is
  never fetched, let alone filtered out.
- **One module builds every response** (`productViewService`): a `full` shape and
  an `assignee` shape, chosen per product. The list, the detail, the delay view
  and every write that returns a product all go through it - including creating a
  product (a creator who isn't the owner gets only `{id, name}`, otherwise the
  response would hand them another user's details), `PATCH`, new versions, and
  transitions (an assignee who advances their stage gets their own view back).
- **Computation runs over the full history; only the output is filtered.** The
  assignee's readiness hint needs the durations of stages they can't see, so
  `computeLiveDelays` always loads the whole history and the projection narrows
  what it *returns*. The assignee view is built from targeted queries and never
  loads versions, approvals or other people's assignments.
- **Readiness** is a small pure function (`readinessService`, 8 unit tests):
  `completed` / `open_now` / `up_next` / `upcoming`, with "opens in ~N days" =
  the unspent part of the current stage + the expected duration of every stage in
  between. It is derived from the product's *current* stage, not from the delay
  computation's per-stage status, because that status uses "latest visit wins" and
  would call a stage "completed" after a rework loop moved the product behind it.
- **Deviation from your test wording: a product with no relationship to the viewer
  is a `404`, not a `403`/empty view.** It is indistinguishable from a product that
  doesn't exist (same status and message, tested), so ids can't be probed. `403`
  is used only where the viewer *can* see the product but lacks authority. A
  malformed id is a `404` too (previously it would have surfaced as a 500).
- **Assigned manager = full view of that product.** Your brief puts "owner (or
  assigned manager, scoped)" in the full tier; ADR 0004's text only described
  owner and assignee, so I followed the brief and recorded it in the ADR: a manager
  can't exercise authority over something they can't see.
- **The assignee view is deliberately minimal** (see the ADR): no product status,
  dates, current stage, owner, versions, approvals, other assignments, stage
  position, or any other user. Notes show only `isMine`, not authors, to
  colleagues. Easy to widen later; hard to narrow once relied on.
- **`GET /stages` would have leaked every stage name to everyone** (it listed all
  definitions). Now: admin, and anyone who sees at least one product in full, get
  all; everyone else gets only the stages they're assigned to.
- **Token role vs. database role.** Last session flagged that the role in a token
  can be up to an hour stale. Authorization now depends on it, so `authenticate`
  loads the user on every request and uses the *current* role (one primary-key
  lookup). A demoted admin stops being one immediately and a deleted user's token
  stops working on every route, not just `/auth/me`. Tested both.

### Part 3 - Authority and write paths

- **Transitions.** Backward, approval decisions and forcing need authority
  (admin / owner / assigned manager), else `403`. A stage with several assignees
  is never fired automatically: once everyone is ready, an authority holder must
  trigger it; if not everyone is ready it is a `409` unless `force: true`, which
  is recorded (`forced_exit`). A stage with one assignee can be advanced by that
  assignee directly, with no ready mark. Everything else an assignee tries is
  `403`. The person who triggered it is stored on the stage they left.
- **Approvals** now use the authenticated actor. `decidedById` in the body is a
  `400` (rejected rather than ignored, as with `role` at registration). The rule is
  admin, the owner *whatever their role*, or an assigned manager; ADR 0005 was
  updated to say this is what the API enforces, replacing the old "coarser than
  the rule" paragraph.
- **Ready marks** target an assignment row, and only that row's own user may set
  it - not an admin either (an admin who wants to move on forces the transition).
  Only the product's *current* stage can be marked, and marks on a stage are
  cleared whenever the product enters it again, so a rework loop needs a fresh
  sign-off. (Both were my calls; the ADR says "each marks themselves ready" and
  nothing about re-entry.)
- **Progress notes**: any assignee of the stage, at any time, and never moving the
  product. Not the owner or an admin unless they're also an assignee.
- **Assignment management is admin-only** (assign, unassign), audited in the
  history table, and checked *before* anything is loaded so a non-admin learns
  nothing about which products or users exist.
- **Things the ADRs are silent on that I had to decide, for safety:** editing,
  deleting or versioning a product needs authority (otherwise any assignee could
  delete a product); changing a product's `ownerId` is admin-only (otherwise an
  assigned manager could make themselves the owner and take local-admin
  authority). All recorded in the ADR's implementation notes.
- **Body fields left as they were, because neither ADR resolves them:** who may
  *create* a product and `ownerId` on creation (any authenticated user, and the
  creator needn't be the owner), `responsibleUserId` on a transition, and

## Step 10 - Frontend login, and rendering the assignee view

### Before Part 1 - CORS

- **The brief said "add CORS"; it was already there, and open.** `app.ts` has had a bare
  `app.use(cors())` since step 1, which reflects *any* origin. It had never mattered
  because nothing real called the API from a browser; with bearer tokens it does. So
  the work was replacing a wildcard with an allowlist.
- `CORS_ALLOWED_ORIGINS` (comma-separated, default the Vite dev origin
  `http://localhost:5173`). Validated at startup like the JWT settings: a `*` is
  refused, and so is anything that isn't a bare origin (a trailing slash or a path
  could never match what a browser sends in `Origin`, so it would silently allow
  nothing). Documented in `.env.example`; `docker-compose.yml` passes it through.
- **What "rejected" means.** CORS is enforced by the browser: the server withholds the
  grant and the browser refuses to give the response to the calling page. A
  disallowed origin gets no `Access-Control-*` headers at all; requests with no
  `Origin` header (curl, server to server) are unaffected. I did *not* return an HTTP
  error for a disallowed origin, because a same-origin deployment (web and API behind
  one host) would send an `Origin` that isn't in the list and be locked out.
- **A test found something.** My first version relied on the `cors` package to refuse
  a disallowed origin. The test failed: for a disallowed *preflight* it still sent
  `Access-Control-Allow-Methods`, just not `Allow-Origin`. Harmless (browsers need
  `Allow-Origin`), but "no useful grant" is not the same as "no grant", so a thin
  wrapper now skips the CORS layer entirely for origins not on the list.
- **A preflight must not need a token.** Browsers send it without credentials; if the
  auth middleware answered it, every call to a protected route would fail with a 401
  that looks exactly like a login bug. Tested for a protected path.
- 8 new tests (`cors.test.ts`) and 8 for the config parsing; mutation-checked by
  reverting to reflect-any-origin (3 fail). Also checked against a real running server
  with browser-style requests: allowed origin echoed back (not `*`), `POST /auth/login`
  preflight answered including `Authorization`, protected-route preflight `204`
  without a token, disallowed origin gets no CORS headers.

### Part 1 - Login flow and token storage

- **Token storage: in memory only.** The access token lives in a module-level variable
  in `api/client.ts`, written only by `AuthProvider`; never `localStorage`,
  `sessionStorage` or a cookie. Reasoning: anything a script can read from storage, an
  injected script can read too, and with a one-hour token and no refresh flow the
  convenience of surviving a reload isn't worth that. **Trade-off, accepted
  explicitly: a hard refresh logs you out** (confirmed in a real browser).
  **Deferred, once a refresh-token flow exists:** silently restoring a session on load,
  and multi-tab logout/refresh coordination.
- **Logout just drops the token.** The API is stateless JWT, so there is no
  server-side revocation to call, and a token copied elsewhere stays valid until it
  expires. That's the deliberate simplicity of a stateless token, not an oversight.
- **The token is set in the client *before* React state changes**, so the first
  request the newly-rendered pages make already carries it. The fetch wrapper attaches
  `Authorization: Bearer` to every authenticated request.
- **401 handling.** An authenticated request that comes back 401 calls a single
  "session ended" handler: drop the token, redirect to login, show "Your session
  expired". Login itself is exempt (a 401 there just means wrong credentials), and a
  stray 401 with no session raises no notice. This covers page loads *and* actions
  (tested with a 401 from "mark ready"). The handler is registered in a layout effect
  so it exists before any child's data-fetching effect runs.
- **A network failure is not a bad password.** `fetch` only rejects when no response
  arrived - the API being down, or the browser blocking it on CORS. That now becomes
  "Could not reach the API at ... is this page's origin allowed by its CORS settings
  (CORS_ALLOWED_ORIGINS)?", so the failure the brief warned about reads as what it is.
- **Routes.** `/login` is public; everything else, including unknown paths, sits behind
  `RequireAuth`, so a logged-out visitor is never told which paths exist. After login
  you return to where you were headed.
- **A bug the tests caught in my own first version:** after a deliberate logout, the
  *next* person to log in was sent to the previous person's page. The login page used
  the "signed out" notice to decide whether to honour the remembered location, but
  logging in clears that notice, so the rule flipped at the worst moment. Fixed at the
  source: `RequireAuth` simply doesn't record a location after a deliberate logout
  (an *expired* session still does - same person, same task).
- Lint flagged writing a ref during render in `AuthProvider`; removed by making the
  token holder itself the source of truth for "is there a session to end".
- **Not built:** proactive logout at token expiry (the login response includes
  `expiresIn`, unused; a 401 is what ends a session), refresh tokens, login rate
  limiting, cross-tab logout.
