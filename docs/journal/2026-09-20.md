## Step 7 — Accept ADR 0004, and fix the PATCH status footgun

### Part 1 — ADR 0004 accepted (docs only)

`docs/architecture/0004-stage-level-access-control.md` moves from Proposed to
Accepted, with all five open questions resolved. No code was touched.

The five decisions, in short:

1. **Visibility** — an assignee sees only their own assigned stages plus a
   server-derived readiness hint ("up next" / "opens in ~N days" / "open now" /
   "completed"); no other stage names or statuses.
2. **Progress vs. transition** — two separate actions. Recording a delay
   reason/status note on your own stage is open to any assignee at any time and
   never moves the product. Advancing is guarded: sole assignee finishing their
   stage can trigger it; with several assignees each sets a `ready_at` on their
   assignment row; admin/manager can force it. Backward moves stay
   admin/manager-only.
3. **Roles vs. assignment** — role gates which kinds of actions/modules you can
   use (e.g. `FINANCE` for Module 3's budgets); assignment gates visibility into
   a product's stage data. Role alone grants no product visibility.
4. **Owner** — full visibility of their own product only ("local admin" for it).
5. **Outside contributors** — ordinary `users` rows with no assignments until
   an admin adds some; no separate account type.

What the rewrite involved beyond flipping the status line:

- The Decision section had to change, not just the questions section. The old
  text said an assignee could record progress only on a stage "the product is
  currently in"; Resolution 2 says "at any time," so that wording was wrong once
  the question was resolved. Also added the `ready_at` column to the
  `product_stage_assignments` sketch and the owner projection.
- The old "Open questions" section became a "Resolution notes" subsection
  (reasoning for each answer, in prose), and the Alternatives section now also
  records the rejected options for Q1(b), Q2 and Q5. The "per-product membership"
  alternative is still rejected for assignees but is now noted as adopted,
  narrowly, for owners.
- A stale line in the Consequences section still described the frontend's
  per-product `/delay` calls, which were removed in step 6; corrected.
- `0005-approval-records.md`: replaced the "revisit when 0004 is accepted"
  bullet with a pointer to 0004's Resolution 2 — the approval gate's
  `ADMIN`/`MANAGER` authority is meant to match "admin/manager can force a
  transition" once real authentication exists. It still says plainly that plain
  backward/forced transitions are not role-gated in the API today.

**Things the resolutions leave open** (written into the ADR as "Points these
resolutions leave for implementation", not decided by me):

- A manager can force/backward-transition, but role alone gives no visibility.
  How can a manager act on a product they can't see? Working assumption in the
  ADR: authority applies to products they own or are assigned to; admin covers
  the rest. Needs confirming.
- Whether an owner's "local admin" status lets them approve or force-transition
  their *own* product — a separation-of-duties question against ADR 0005, which
  restricts approvals to `ADMIN`/`MANAGER`.
- Who triggers the transition once every assignee of a multi-assignee stage is
  ready.
- Where progress notes are stored relative to `ProductStageHistory.delay_reason`.

Dating: the ADR's "Accepted" date and this journal are dated 2026-09-20, the day
these are being committed, rather than the day the text was written.

### Part 2 — PATCH /products/:id status footgun

`PATCH` accepted `status: "DELAYED"` / `"ON_TRACK"` and returned 200 with the
new value, but since step 6 reads compute status from delay, so the write had no
lasting effect — a silent no-op that looked like it worked. Now
`productService.updateProduct` rejects it with a `400`: "status is derived from
delay computation; only BLOCKED can be set manually". The check lives in the
service (a business rule), before any write, so a rejected request applies none
of its other fields either (there's a test for that).

**One deliberate deviation from "reject DELAYED/ON_TRACK".** `BLOCKED` always
wins over the derived value, so the only way to *clear* a block was previously a
`PATCH` with `ON_TRACK`/`DELAYED`. Rejecting both outright would have left any
blocked product blocked forever. So `ON_TRACK` is still accepted — but only on a
product that is currently `BLOCKED`, where it means "clear the block". The value
stored is then whatever the delay computation says (`ON_TRACK` *or* `DELAYED`),
never the raw value sent; an overrun product cleared this way comes back
`DELAYED` (tested). `DELAYED` is always rejected. If a different unblock
mechanism is preferred later (say, an explicit `blocked` flag or an
`/unblock` action), this is the one branch to replace.

- **Tests:** replaced the old "updates product status" test (which asserted the
  footgun) with: DELAYED → 400 with the message; ON_TRACK on an unblocked
  product → 400; BLOCKED accepted; DELAYED rejected on a blocked product and
  ON_TRACK clears it and re-derives; other fields still apply alongside a valid
  status; nothing applies when the status is rejected. Plus one in
  `liveStatus.test.ts` for the overrun-then-unblocked case. Confirmed these fail
  with the guard removed (4 do).
- **shared-types:** no change — there's no request type for `PATCH` fields in the
  package, so no shape to update. Worth adding one when the frontend gets write
  flows.
- README: the `PATCH` row now describes the rule.

**A bug in my own earlier work, found and fixed along the way.** The first
attempt at this edit failed with a `UnicodeDecodeError`: `productService.ts`
contained a lone `0x97` byte. Cause: last session's Python edit scripts opened
files without an explicit encoding, so on Windows they were read/written as
cp1252, and where the *replacement text* contained an em dash it was written as
a single cp1252 byte instead of UTF-8. Scanned every tracked file: exactly two
were affected, both mine and both already committed on the branch —
`apps/api/src/services/productService.ts` and
`packages/shared-types/src/index.ts`, one comment line each (they'd have
compiled, showing a replacement character in the comment). Fixed at the byte
level; no other file was affected, and no mojibake (`â€”`) anywhere. Lesson: pass
`encoding='utf-8'` explicitly when scripting file edits on Windows.

## Step 7, continued — the four remaining ADR 0004 points, then committing

### Part 1 — ADR 0004 follow-up resolutions (docs only)

The four points the acceptance left open are now settled in
`docs/architecture/0004-stage-level-access-control.md` (a "Follow-up
resolutions" subsection, numbered 6–9 after the original five), and the ADR's
Status line now says all of them are resolved. No code changed.

6. **Manager authority is scoped to visibility.** A manager can force a
   multi-assignee transition or go backward only on products they own or are
   assigned to; only an admin is unscoped. Chosen over blind manager authority so
   a second access model doesn't grow beside the visibility one.
7. **Owner's local-admin status extends to approvals** on their own product
   (approval gate = admin, the product's owner, or an assigned manager).
   Consequence written into the ADR: an owner can approve their own product — no
   separation of duties, a conscious trade-off.
8. **A fully signed-off multi-assignee transition needs a manual trigger** — not
   an auto-fire on the last `ready_at`, which would attribute the transition to
   whoever happened to sign off last when nobody decided to advance the product.
9. **Progress notes get their own table**, `stage_progress_notes` (`id`,
   `product_id`, `stage_id`, `user_id`, `note`, `created_at`), rather than reusing
   the deferred `comments` table; they're scoped functional data read by the
   readiness/delay views, so this doesn't reopen the `comments` deferral in
   ADR 0005.

Beyond appending the four items, the rest of the ADR had to be brought in line
so it doesn't contradict itself: Decision item 4 previously said "admin or
manager can force it" and "the transition proceeds once all are ready", both
superseded; Resolution 2's wording, the Consequences and the Alternatives
(three new rejected options) were updated too. I introduced one term to keep the
rules from being restated four times: **"authority over a product"** = admin
(unscoped) ∪ the product's owner ∪ a manager assigned to it. Forcing, backward
moves, triggering a signed-off transition and approval decisions all use that
one set.

**One inference of mine to confirm.** Resolutions 6 and 8 as given name only
"admin, or the owning/assigned manager". I included the *owner* (whatever their
role) in that set for forcing/backward/triggering as well, because Resolution 4
makes the owner a local admin and Resolution 7 already puts them in the approval
gate — otherwise the owner could approve a product but not advance it, which
seemed unintended. If owners should *not* be able to force or reverse
transitions, that's a one-line change in the ADR's "authority over a product"
definition.

`0005-approval-records.md`: the "Who can decide" paragraph now states the target
rule ("admin, the product's owner, or an assigned manager"), and says plainly
that the current implementation is coarser — any `ADMIN`/`MANAGER` user for any
product — until authentication and assignment data exist, with the practical
effect spelled out (an owner who isn't a manager/admin gets 403 today; an
unrelated manager is allowed). The Consequences bullet was updated and an
"owner can approve their own product" bullet added.
