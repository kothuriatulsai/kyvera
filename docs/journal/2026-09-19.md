# 2026-09-19

## Step 5 — Minimal React frontend

Three read-only views over the existing API: product list, "what's currently
delayed," and a product detail page with a stage timeline.

### What was attempted

- **`GET /stages`** — the one API addition. The `/delay` breakdown is keyed by
  `sequenceOrder`, and the product detail response only carries names for
  stages the product has already visited, so a timeline showing *upcoming*
  stages had no source for their names. Added it through the usual
  `routes → controllers → services → repositories` layers (reusing
  `stageDefinitionRepository.findAll`) plus a small integration test.
- **`packages/shared-types`** — was an empty `export {}` since step 1. It now
  holds the JSON response shapes (`ProductSummary`, `ProductDetail`,
  `ProductDelay`, ...) and the web app consumes it as a workspace dependency.
  Used string-literal unions instead of enums because the web tsconfig has
  `erasableSyntaxOnly`. Dates are typed as ISO strings, since that's what's on
  the wire. Note the API doesn't import these yet — they're hand-mirrored from
  the Prisma models, so they can drift; worth revisiting when Module 2 adds
  more shapes.
- **Web app** — React Router (added as a dependency; three routes didn't seem
  worth hand-rolling a router for), a thin `fetch` wrapper that surfaces the
  API's `{ error }` messages, a small `useAsync` hook, and one page per view.
  Plain CSS with `color-scheme: light dark`; no component library.
- **Tests** — `App.test.tsx` now stubs `fetch` and renders each route
  (replacing the scaffold's "renders the heading" test, which no longer
  applied): list, delayed-only filtering, the timeline's per-stage delay, and
  the API-error path.

### What broke / notable decisions

- **The persisted `products.status` goes stale.** It's only recomputed on
  create and on transition, so a product that has sat in one stage past its
  expected duration since its last transition is still `ON_TRACK` in the
  database — exactly the product the "delayed" view exists to find. Only
  `GET /products/:id/delay` is live. The list and delayed views therefore call
  `/delay` once per product and derive the status from that (falling back to
  the stored status for a row whose lookup fails). That's an N+1 from the
  browser, fine at this scale but the wrong long-term shape; the proper fix is
  computing delay server-side in `GET /products` (or a `?delayed=true` filter)
  and probably a scheduled recompute so the stored status is trustworthy.
  Left as a follow-up rather than reworking step 4's service mid-frontend.
- First version of `useAsync` called `setState` synchronously inside its
  effect to reset to "loading," which oxlint flagged. Reworked it to tag each
  result with the request key and derive "loading" when the key doesn't match
  the current one — which also means a stale response can't be rendered as
  current.
- **Not verified in a browser.** Typecheck, lint, the production build and the
  web tests pass, but Docker wasn't running, so the new `stages` integration
  test and a click-through against a live API were not run.

### What's next

Module 1's build order is now complete except for polish: write flows in the UI
(create a product, transition a stage — currently API-only) and the
server-side delay fix above. Auth (hand-rolled JWT + roles) is its own item
before Module 2 starts.

## Idea parked: stage-level access control

Came up while looking at the Solar Charger timeline: each stage is worked by
different people (sometimes one person for several stages, sometimes several
people on one stage), and contributors should only see the stages they're
assigned to, with only an admin seeing everything and managing assignments.
Not being built now — written up as
[ADR 0004](../architecture/0004-stage-level-access-control.md) (status:
Proposed). Conclusion: it belongs in a cross-cutting access-control module
alongside the planned JWT auth, after Module 1 and before Module 2, because it
needs authenticated identity first and every later module needs the same
"who is asking" question. The ADR lists five open questions to settle first,
the main one being how much a contributor may know about the rest of the
product's progress.

## Step 6 — Approvals and live status

### Part 1 — ADR 0005 (approval records)

Wrote `docs/architecture/0005-approval-records.md`: an append-only `approvals`
table (product, exact product version, the Approval stage, `APPROVED`/
`REJECTED`, decider, timestamp, notes) that is created in the same transaction
as the transition into the final stage. Module 2's handoff query becomes
"does an `APPROVED` row exist for this product + this exact version," reusing
the existing version-pinning design. `comments` and `attachments` are
explicitly deferred in the same ADR — nothing downstream depends on them, and
`attachments` needs a storage decision that shouldn't be made speculatively.

Things worth recording that the ADR had to work around:

- **ADR 0004's Q2 is not resolved in the repo** (it's still "Proposed" with
  all five questions open), so there is no "multi-assignee sign-off override"
  to be consistent with. ADR 0005 states the approval gate as admin/manager
  only, on its own terms, and says it should be revisited when 0004 is
  accepted. Left 0004 untouched, as asked.
- **"Same gate as any backward transition" isn't true yet** — plain backward
  transitions aren't role-gated today. ADR 0005 says so rather than implying it,
  and doesn't add that gate.
- **There is no authenticated actor**, so the admin/manager check can only be
  made against a `decidedById` field in the request body. That's a business-rule
  gate, not a security boundary; the ADR states this and says the field goes
  away once JWT auth lands.
- **"The Approval stage" = the final stage** (highest `sequence_order`), not a
  stage looked up by name, to stay consistent with stages-as-data (ADR 0003).
  The ADR notes the fix (a `requires_approval` flag) if a stage is ever added
  after Approval.

### Part 2 — Implementing approvals

- **Schema/migration**: `Approval` model + `ApprovalDecision` enum
  (`approvals` table), migration `add_approvals`. FKs to product/version cascade
  on delete (so `DELETE /products/:id` still works), `stage`/`decidedBy` don't.
  Indexed on `(product_id, product_version_id)` for the Module 2 lookup. Note
  `prisma migrate dev` applied the migration but did *not* regenerate the client
  here — had to run `prisma generate` before typecheck would see the new model.
- **`stageTransitionService`**: the approval decision only *resolves the
  direction* and adds one write inside the existing transaction — there is no
  second transition path. Order of checks: approval on a non-approval move → 400;
  entering the final stage without one → 400; decider must exist (400) and be
  ADMIN/MANAGER (403 — new `ForbiddenError`); REJECTED needs notes, then flips
  `direction` to `"backward"` and uses the notes as the backward `reason`, and
  everything below (history close/open, `delayReason`, delay recompute) runs
  unchanged. The Approval stage is found as the highest `sequence_order`
  (`stageDefinitionRepository.findLast`), not by name. The approval row is
  written in the same transaction, pinned to the product's current version.
- **`approvalRepository`** (create only — append-only by design, no
  update/delete) following the optional-`Db` pattern; `GET /products/:id` now
  includes `approvals` (decider via `safeUserSelect`, plus the version number).
- **Tests** (`tests/approvals.test.ts`, 8): required-to-enter, APPROVED-then-
  forward (also asserts the row is pinned to the exact version id and final
  stage), REJECTED-then-backward (asserts notes became the `delayReason`),
  notes-required-to-reject, engineer → 403 with nothing moved or recorded,
  unknown decider / bad decision → 400, approval on a non-approval move → 400,
  and reject → new version → re-approve leaves the v1 rejection and pins the
  approval to v2. Sanity-checked that the 403 test can fail by temporarily
  adding ENGINEER to the allowed roles — it did.
- **shared-types**: `Approval`, `ApprovalDecision`, `ApprovalRequest`;
  `ProductDetail` gains `approvals`.

**Caveat carried over from the ADR**: the gate checks the role of the user named
in `decidedById`, and there is no authentication, so it enforces the business
rule but is not access control. It becomes real once JWT auth exists.

### Part 3 — Live status, server-side

**The problem** (from the step 5 entry): `products.status` is only persisted on
create/transition, so a product that overran its current stage without
transitioning read `ON_TRACK`, and the frontend papered over it with one
`/delay` request per product.

**Decision: compute per request, batched — not a scheduled recompute.**

- *Per-request (chosen).* `GET /products` and `GET /products/:id` call
  `productDelayService.withLiveDelay`: one query for the stage definitions, one
  for the history of every listed product, then the existing pure
  `computeProductDelay` per product in memory. Correct by construction — the
  answer can't be older than the request. Cost is O(products × stages) of
  trivial arithmetic plus two queries regardless of list size; fine for an
  internal tool with tens or hundreds of products.
- *Scheduled recompute (rejected).* Needs a scheduler process, a story for
  running it once when there are several API instances, and still leaves a lag
  window between runs — so the stored column would be *less* stale but never
  live, and we'd own an operational component to get a weaker guarantee.
- *When to revisit:* if the list gets big enough that computing per request
  hurts, or we need to filter/sort by status **in SQL** (the stored column is now
  only a snapshot, so a `WHERE status = 'DELAYED'` would be wrong). At that point
  a recompute job or a materialised view is justified — and it would still call
  the same delay service.

**No duplicated logic.** The status rule (BLOCKED sticks, otherwise status follows
delay) is now one function, `deriveStatus`, used by both the persist-on-transition
path and the live read path; the DB-row → computation-input adapter
(`toDelayInput`) is likewise shared with the single-product path.

**API shape.** Read responses gain `delay: { delayed, totalDelayDays,
expectedCompletionDate }` so the delayed view needs no per-product call. The
shared types split accordingly: `ProductSummary` (stored, in write responses) vs
`ProductListItem` (reads, live) vs `ProductDetail` (extends the latter).

**Frontend.** Removed `useProductsWithDelays`, `effectiveStatus` and the N+1;
list/delayed pages just `fetchProducts()`. The list's date column now shows the
live projection (the stored `expectedCompletionDate` goes stale in the same
way, and is also a manual target when set at creation, so it isn't a good thing
to display). Web tests now assert those pages make exactly one request.

**Side effects worth knowing:**
- `PATCH /products/:id` with `status: "DELAYED"`/`"ON_TRACK"` no longer has any
  visible effect on reads — status follows delay; only `BLOCKED` is a real manual
  state. The existing PATCH test still passes because it only asserts the PATCH
  response, which is the stored value. Not changed here; worth tightening
  (reject or ignore non-BLOCKED manual statuses) when access control lands.
- Write responses (create/update/transition) still return the stored snapshot, not
  the live overlay. On transition the two agree, since the transition just
  recomputed and persisted.
