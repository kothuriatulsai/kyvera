# 2026-09-19

## Step 5 — Minimal React frontend

Three read-only views over the existing API: product list, "what's currently
delayed," and a product detail page with a stage timeline.

### What was attempted

- **`GET /stages`** — the one API addition. The `/delay` breakdown is keyed by
  `sequenceOrder`, and the product detail response only carries names for
  stages the product has already visited, so a timeline showing *upcoming*
  stages had no source for their names. Added it through the usual
  `routes → controllers → services → repositories` layers (reusing
  `stageDefinitionRepository.findAll`) plus a small integration test.
- **`packages/shared-types`** — was an empty `export {}` since step 1. It now
  holds the JSON response shapes (`ProductSummary`, `ProductDetail`,
  `ProductDelay`, ...) and the web app consumes it as a workspace dependency.
  Used string-literal unions instead of enums because the web tsconfig has
  `erasableSyntaxOnly`. Dates are typed as ISO strings, since that's what's on
  the wire. Note the API doesn't import these yet — they're hand-mirrored from
  the Prisma models, so they can drift; worth revisiting when Module 2 adds
  more shapes.
- **Web app** — React Router (added as a dependency; three routes didn't seem
  worth hand-rolling a router for), a thin `fetch` wrapper that surfaces the
  API's `{ error }` messages, a small `useAsync` hook, and one page per view.
  Plain CSS with `color-scheme: light dark`; no component library.
- **Tests** — `App.test.tsx` now stubs `fetch` and renders each route
  (replacing the scaffold's "renders the heading" test, which no longer
  applied): list, delayed-only filtering, the timeline's per-stage delay, and
  the API-error path.

### What broke / notable decisions

- **The persisted `products.status` goes stale.** It's only recomputed on
  create and on transition, so a product that has sat in one stage past its
  expected duration since its last transition is still `ON_TRACK` in the
  database — exactly the product the "delayed" view exists to find. Only
  `GET /products/:id/delay` is live. The list and delayed views therefore call
  `/delay` once per product and derive the status from that (falling back to
  the stored status for a row whose lookup fails). That's an N+1 from the
  browser, fine at this scale but the wrong long-term shape; the proper fix is
  computing delay server-side in `GET /products` (or a `?delayed=true` filter)
  and probably a scheduled recompute so the stored status is trustworthy.
  Left as a follow-up rather than reworking step 4's service mid-frontend.
- First version of `useAsync` called `setState` synchronously inside its
  effect to reset to "loading," which oxlint flagged. Reworked it to tag each
  result with the request key and derive "loading" when the key doesn't match
  the current one — which also means a stale response can't be rendered as
  current.
- **Not verified in a browser.** Typecheck, lint, the production build and the
  web tests pass, but Docker wasn't running, so the new `stages` integration
  test and a click-through against a live API were not run.

### What's next

Module 1's build order is now complete except for polish: write flows in the UI
(create a product, transition a stage — currently API-only) and the
server-side delay fix above. Auth (hand-rolled JWT + roles) is its own item
before Module 2 starts.

## Idea parked: stage-level access control

Came up while looking at the Solar Charger timeline: each stage is worked by
different people (sometimes one person for several stages, sometimes several
people on one stage), and contributors should only see the stages they're
assigned to, with only an admin seeing everything and managing assignments.
Not being built now — written up as
[ADR 0004](../architecture/0004-stage-level-access-control.md) (status:
Proposed). Conclusion: it belongs in a cross-cutting access-control module
alongside the planned JWT auth, after Module 1 and before Module 2, because it
needs authenticated identity first and every later module needs the same
"who is asking" question. The ADR lists five open questions to settle first,
the main one being how much a contributor may know about the rest of the
product's progress.
