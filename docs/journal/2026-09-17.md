## Step 2 — Prisma schema, migration, and dev environment

Implemented the five Module 1 models from the architecture doc
(`User`, `StageDefinition`, `Product`, `ProductVersion`,
`ProductStageHistory`) in `apps/api/src/prisma/schema.prisma`, ran the first
migration against a Dockerized Postgres, and got the rest of the dev
environment (seed data, CI, client wiring) working end to end.

### What was attempted

- Resolved the step-1 `prisma/` location question: kept it at
  `apps/api/src/prisma/` per the architecture doc, and pointed Prisma's CLI
  at it via `apps/api/prisma.config.ts` (`schema`, `migrations.path`,
  `migrations.seed`) instead of relying on the default `apps/api/prisma/`
  location.
- Modeled the five entities with Postgres-native types (`@db.Uuid` PKs/FKs,
  native enums for `UserRole` / `ProductStatus`) and `@map`/`@@map` so the
  Prisma layer is camelCase while the actual tables/columns stay the
  snake_case names from the architecture doc.
- `StageDefinition` and `ProductStageHistory` implement the "stages as
  data" design directly — see `docs/architecture/0003-workflow-stages-as-data.md`.
- `ProductVersion` is what `manufacturing_orders` (Module 2) will
  eventually pin to, per the doc's explicit versioning requirement.
- Ran `prisma migrate dev --name init` against Postgres via
  `docker compose up -d postgres`; verified all 5 tables exist and query
  correctly with `psql`.
- Added `apps/api/src/prisma/seed.ts` with the nine workflow stages
  (Requirement → ... → Approval) and placeholder `expected_duration_days`
  values, wired to `prisma db seed` via `prisma.config.ts`.
- Added a shared Prisma client singleton (`src/repositories/prismaClient.ts`)
  guarded against creating duplicate clients across `tsx watch` reloads.
- Updated CI to spin up a Postgres service container, run
  `prisma migrate deploy` before tests, so the pipeline stays representative
  of a real DB-backed test run once repository/service tests exist.

### What broke / notable decisions

- **Prisma 7 breaking change**: `datasource.url` is no longer allowed
  directly in `schema.prisma` — connection URLs now belong in
  `prisma.config.ts`, and `PrismaClient` requires an explicit driver
  adapter rather than connecting via a bundled query engine binary. Added
  `@prisma/adapter-pg` + `pg`, and the client singleton now does
  `new PrismaClient({ adapter: new PrismaPg({ connectionString: ... }) })`.
  This is a real architectural shift (Prisma moving off its Rust query
  engine toward driver adapters) worth remembering for anyone following
  older Prisma tutorials/docs against this codebase.
- `prisma generate` runs as a `postinstall` script, which means
  `DATABASE_URL` must be resolvable (even to a non-existent DB) at
  `npm install` time — `prisma.config.ts` loads `dotenv/config` itself
  since Prisma's config-file-based CLI no longer auto-loads `.env` the way
  older versions did. CI sets `DATABASE_URL` at the job level so this
  works before the Postgres service is even queried.
- Chose UUID (`@db.Uuid`, client-generated `uuid()`) over autoincrement
  integers for primary keys — slightly more friction to eyeball in `psql`,
  but avoids ID collisions across future distributed/import scenarios and
  is the more realistic choice for a system meant to demonstrate real
  relational design.
