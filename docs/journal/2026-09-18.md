# 2026-09-18

## Step 3 — Product CRUD and the stage-transition endpoint

Implemented the full `routes → controllers → services → repositories`
layering for products, matching the request flow from the architecture doc.

### What was attempted

- **Repositories** (`src/repositories/`): `productRepository`,
  `productVersionRepository`, `productStageHistoryRepository`,
  `stageDefinitionRepository`, `userRepository` — thin Prisma wrappers, each
  function taking an optional `Db` (the shared client or a
  `$transaction` callback's `tx`) so services can compose atomic multi-model
  writes without repositories knowing about transactions themselves.
- **Services**: `productService` (list/get/create/update/delete a product,
  create a new `ProductVersion`) and `stageTransitionService` (the
  `POST /products/:id/transition` logic). `createProduct` is transactional:
  product row + v1 `ProductVersion` + the first `ProductStageHistory` entry
  (for `sequence_order = 1`) all get created together.
- **Transition logic**: `direction` is `"forward"` (default) or
  `"backward"`, and always moves exactly one `sequence_order` step — there's
  no "jump to stage X" path, which is what makes "can't skip stages" true
  by construction rather than a validated invariant. Moving forward past
  the last stage or backward past the first is a 400. Backward requires a
  non-empty `reason`; forward closes the current `ProductStageHistory` entry
  (`exitedAt`, `actualDurationDays`, `delayed` if it ran over
  `expectedDurationDays`) and opens a new one for the target stage, all
  inside one `prisma.$transaction`.
- **Errors**: a small `AppError`/`NotFoundError`/`ValidationError`/
  `ConflictError` hierarchy in `services/errors.ts` — deliberately
  Express-free so services stay framework-agnostic. `app.ts` has one
  catch-all error middleware that maps these to status codes, plus a
  fallback 404 handler and a `Prisma.PrismaClientKnownRequestError` (P2025)
  → 404 mapping.
- **Cascade deletes**: added `onDelete: Cascade` on `ProductVersion.product`
  and `ProductStageHistory.product` (new migration) so `DELETE /products/:id`
  actually works instead of hitting an FK violation.
- **Tests**: `tests/products.test.ts` — a real Supertest suite against the
  running app + a live Postgres (create → list → reject bad `ownerId` →
  transition forward → reject backward-without-reason → transition backward
  → reject past-first-stage → new version → update status → reject bad
  status → delete → 404). Verified the exact same flow manually via `curl`
  first, then again against a fully fresh `docker compose down -v` database
  to make sure `migrate deploy` + `db:seed` + `test` (the CI sequence)
  actually works from zero, not just against my already-migrated dev DB.
- Fixed a real bug caught while writing the first manual `curl` test: the
  nested `owner`/`responsibleUser`/`createdBy` objects in API responses
  were including the full `User` row — `passwordHash` and all. Added
  `repositories/selects.ts` (`safeUserSelect`) and switched every user
  relation `include` to a `select`. Worth remembering: `include: true` on a
  relation always returns every column, so any endpoint returning a User
  (even a placeholder-password one, pre-auth) needs this.
- Also fixed a config gap from step 1: `apps/api/package.json`'s
  `typecheck` script ran `tsc --noEmit` against `tsconfig.json`, which
  excludes `tests/` (that tsconfig's job is scoping the production
  `build`). That meant test files were never type-checked, in CI or
  locally. Added `tsconfig.typecheck.json` (includes `src` + `tests`) and
  pointed `typecheck` at it.

### What broke / notable decisions

- CI needed a new `Seed database` step (`db:seed` after `db:deploy`, before
  `test`) — `products.test.ts` depends on `stage_definitions` already
  being populated (it throws a clear error in `beforeAll` if the table's
  empty, rather than failing confusingly on a null `firstStage`).
- Hit a harmless-but-noisy `DeprecationWarning: Calling client.query() when
  the client is already executing a query` from `pg` during
  `prisma.$transaction`, traced (via `--trace-deprecation`) to Prisma 7's
  new pure-JS query-interpreter (`@prisma/client-engine-runtime`) talking to
  `@prisma/adapter-pg`, not to anything in this codebase's transaction code
  (each repository call inside `$transaction` callbacks is properly
  `await`ed, sequential, one connection). Left as-is — tests pass
  consistently, this is an upstream Prisma 7 / node-postgres interaction on
  a very recently released major version, not a bug in the transition
  service. Worth re-checking on a future `prisma` version bump.
- No auth module exists yet, so `ownerId` / `responsibleUserId` /
  `createdById` are plain request fields validated only by "does this user
  id exist" — anyone can create a product as anyone. Acceptable for now;
  the tech stack doc treats hand-rolled JWT + role auth as its own
  build item, not part of Module 1's step 3.
- Deliberately did *not* build the delay-cascade computation here beyond
  the single closed `ProductStageHistory.delayed` flag
  (`actualDurationDays > expectedDurationDays`) — recomputing
  `Product.expectedCompletionDate` from cascading delays is explicitly
  step 4's "delay computation service," which the architecture doc calls
  out as its own isolated, unit-tested piece.

## Step 4 — Delay computation service

The doc calls this one out explicitly as "the best showcase logic" and asks
for unit tests first, so that's the order it happened in: wrote
`tests/delayComputationService.test.ts` against a contract that didn't exist
yet, then implemented `src/services/delayComputationService.ts` to satisfy
it, then wired it into the rest of the app.

### What was attempted

- **`delayComputationService.ts`** — one pure function, `computeProductDelay`,
  zero DB/Express imports, took no debugging to get right because the tests
  were written first: given a `startDate`, the full list of stage
  definitions, and the product's stage-history rows, it returns a projected
  `expectedCompletionDate` plus a per-stage breakdown. Per stage:
  - `completed` (has an `exitedAt`) → use the stored `actualDurationDays`.
  - `in_progress` (open history entry) → `max(expectedDurationDays, elapsed)`.
    Below the expected duration, project it finishing on time; once it's
    actually run over, cascade the real overage instead of pretending it's
    still on schedule.
  - `not_started` (no history row yet) → `expectedDurationDays` (assume
    on-schedule until proven otherwise).
  - If a stage was visited more than once (moved backward, reworked, moved
    forward again), only the *most recent* visit counts — handles rework
    loops without double-counting or needing special-case logic.
  - 7 unit tests cover: full on-schedule projection with no history,
    early-finish, cascading a completed stage's overage, in-progress
    on-schedule vs. in-progress already-delayed, the rework/re-entry case,
    and summing delay across multiple delayed stages.
- **`productDelayService.ts`** — the Prisma-aware glue layer: fetches the
  product/stage-definitions/history, adapts them into the pure function's
  input shape, and either just returns the result
  (`computeDelayForProduct`, used by the new read-only endpoint) or also
  persists it (`recomputeAndPersistProductDelay`, writes
  `expectedCompletionDate` and `status` back onto the product — leaves
  `status` alone if it's `BLOCKED`, since that's a manually-set state the
  recompute shouldn't clobber).
- **Wired into the existing write paths**, not bolted on separately:
  - `productService.createProduct` calls it inside the same transaction,
    right after the first `ProductStageHistory` entry is created — unless
    the caller passed an explicit `expectedCompletionDate` (a manual
    target should stay a manual target until the first real stage timing
    exists to recompute from).
  - `stageTransitionService.transitionProduct` calls it at the end of its
    transaction, after the stage-history close/open and `currentStage`
    update — this is the natural "a stage's timing just became known"
    trigger point per the architecture doc's own language ("recompute...
    whenever a stage is delayed").
- **New endpoint**: `GET /products/:id/delay` — read-only, always live
  (recomputes on every call rather than reading the persisted snapshot),
  returns the full per-stage breakdown. The persisted
  `products.expected_completion_date`/`status` cover "what's the answer,"
  this endpoint covers "why" — kept as two separate things rather than
  bloating the base product response.
- **Verified live, not just via unit/integration tests**: started the dev
  server, created a product (confirmed `expectedCompletionDate` landed
  exactly `startDate + 56 days`, the sum of all nine seeded stages'
  `expectedDurationDays`), then directly backdated its open stage-history
  row's `entered_at` by 9 days in `psql` to simulate a real delay past the
  5-day `Requirement` stage, confirmed `GET .../delay` showed
  `delayed: true, totalDelayDays: 4` with the cascade correctly reflected
  in `expectedCompletionDate`, then transitioned it forward and confirmed
  the product's persisted `status` flipped to `DELAYED` and
  `expectedCompletionDate` matched the live computation exactly.
- Added 2 more integration tests to `products.test.ts` covering the
  creation-time auto-projection and the `/delay` endpoint's shape.

### What broke / notable decisions

- Nothing broke, notably — the test-first order the doc suggested for this
  step actually worked exactly as advertised: by the time
  `delayComputationService.ts` existed, all 7 tests passed on the first
  run, and wiring it into `productService`/`stageTransitionService`
  afterward didn't require touching the pure function at all.
- Deliberately did *not* make `expectedCompletionDate` fully
  system-managed (i.e. rejecting manual writes outright) — `PATCH
  /products/:id` can still set it directly. That's an intentional escape
  hatch, not an oversight: it's inherently transient anyway, since the
  next transition recomputes and overwrites it regardless.
- `computeProductDelay`'s "most recent visit wins" rule for stages visited
  more than once was a deliberate, documented choice (see the rework-loop
  unit test) rather than, say, summing every visit's duration — summing
  would double-count a stage a product bounced through multiple times,
  which doesn't match what "how long did this stage actually take" should
  mean.
