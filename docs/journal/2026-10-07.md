# 2026-10-07

## Step 23 — Revising ADR 0011 before merge: generated passwords, forced changes, explicit role-change confirm

Review feedback on `feat/user-management` before merging, four changes:

### 1. An admin no longer sets anyone's password

The first pass had `POST /users/:id/reset-password` take a new password chosen by the admin.
Replaced: it now takes no body, generates a one-time temporary password
(`passwordService.generateTemporaryPassword`, 16 random URL-safe characters) and returns it
exactly once in the response - nothing persists it in plaintext, there is no way to see it
again. Sets a new `users.mustChangePassword` column.

Added the self-service side: `POST /auth/change-password` (current + new password), any
authenticated user, their own account only. It's the one way to clear `mustChangePassword`.
Added a new `requirePasswordChanged` middleware, mounted right after `authenticate` in
`routes/index.ts`, that 403s every route behind it while the flag is set; `/auth/me` and
`/auth/change-password` are untouched by it because they authenticate directly inside
`authRoutes`, mounted *before* that middleware exists in the chain, not because of an
exemption list anywhere.

**A real bug, not just a test nuisance**: the existing password-invalidation check compared
the JWT's standard `iat` (whole seconds) against `passwordChangedAt`. A reset landing in the
same wall-clock second as the login that preceded it made the comparison ambiguous and let
the stale token through - reproduced by the very test written to prove the reset invalidates
the old token. Fixed by adding a custom `iatMs` (milliseconds) claim to the token instead of
trying to round the comparison correctly; there's no granularity where whole-second JWT `iat`
and a wall-clock `Date` are safely comparable when both events can happen in the same request
cycle, in a fast automated flow or in practice.

Web: `UserRow`'s reset-password control no longer takes typed input - clicking "Reset
password" calls the endpoint directly and reveals the generated password inline, with a
"won't be shown again" note and a "Done" dismiss. New `AccountPage` (`/account`) for any
logged-in user: profile summary plus a change-password form, reachable even while
`mustChangePassword` is set (that's the whole point of it). `RequireAuth` redirects every
other route to it while the flag is set.

### 2. Explicit role-change confirmation

`UserRow`'s role `<select>` used to submit on change. Now it holds the chosen role as pending
local state; a "Change" button (disabled until the selection actually differs) reveals an
inline "Change X's role to Y?" with its own Confirm/Cancel, and only Confirm calls the API.
Fixed a lint warning along the way (`react(set-state-in-effect)`) by adjusting the row's local
state during render when the `user.role` prop changes externally, rather than in a `useEffect`
- the pattern React's own docs recommend for "reset state when a prop changes."

### 3. Resyncing the session on a 403 or window focus

`api/client.ts` gained a `setForbiddenHandler` next to the existing 401 one. `AuthProvider`
wires both it and a `window.addEventListener('focus', ...)` to the same `resync`: re-fetch
`GET /auth/me`, replace `session.user` wholesale, and if the role changed, show a dismissible
"Your role was changed to X" notice. This is also what makes a `mustChangePassword` flip (an
admin resets someone's password while they're active in another tab) take effect without a
manual reload - it falls out of replacing the whole user object, not a separate code path.

### 4. `/users` renders as 404 for a non-admin, not the API's 403

New `RequireRole` component, mounted inside `RequireAuth` around the `/users` route: checks
`session.user.role` client-side and renders the same `NotFoundPage` the catch-all route uses
(extracted so both share it) rather than letting `UsersPage` make its request and show the
403. This is a deliberate, narrow exception to "the UI doesn't gate, the server does" - every
earlier SOP screen gated *actions* that way, but `/users` is the first page where even
*reading* it is restricted, and confirming a restricted route's existence to someone it
doesn't apply to is itself the thing being avoided here.

## Step 24 — The same gap existed on the create side

Spotted right after Step 23: `createUser` still took an admin-chosen `temporaryPassword` and
left `mustChangePassword` false, so an admin creating an account knew the user's real password
from day one - exactly the trust problem Step 23 had just fixed for resets, just not reached
yet on the other endpoint.

Made `POST /users` match `POST /users/:id/reset-password` exactly: no password field in the
request at all, `userManagementService.createUser` generates one with the same
`generateTemporaryPassword`, sets `mustChangePassword = true`, and returns it once in the
response. Renamed the shared response shape from `ResetPasswordResponse` to
`TemporaryPasswordResponse` in shared-types, since both endpoints return it now.

`assertPasswordPolicy` dropped out of `createUser` entirely - nothing admin-typed is being
validated there anymore, same reasoning as the reset path already had.

Web: `NewUserForm` lost its temporary-password field and gained the same one-time reveal
`UserRow`'s reset-password control already has (shown once, "Done" returns to a fresh form).

Test fallout, mostly in the `createUserViaApi` test helper: since every created user now
starts in the forced-password-change state, the helper changed from "POST /users with a known
password" to "POST /users, log in with the generated one, immediately complete the forced
change to a known password" - every *other* test using that helper (role change, deactivate,
reset, inactive-user) needed no changes at all, because they only ever cared about getting a
normal, usable test account out of it, not how it got that way.
