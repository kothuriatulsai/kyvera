# 2026-10-09

## Step 27 — Project membership and stage-level visibility (ADR 0013)

Slice A's authorization has been "any authenticated user may read" since ADR 0007, deliberately
provisional - no stated confidentiality need yet, and ADR 0007 point 6 / ADR 0009 both explicitly
left the door open to revisit it. The need showed up: Finance/Merchandiser should only see their
own Proto Requests, Management shouldn't see a Tech Pack mid-review, and nobody should see a
Project they have nothing to do with. Built it as two layers in one module
(`services/visibility.ts`), per the plan: layer A (`ProjectMember`) decides which Projects a role
sees at all - ADMIN/PMO/MANAGEMENT see everything, everyone else needs a membership row; layer B
decides which *parts* of a visible Project's Tech Packs a role sees, and when. Full design and the
endpoint x role matrix are in ADR 0013.

### The plan's amendments, as built

1. **ProtoRequest is now self-contained.** `techPackVersion` carries `attachments`/`approval`
   directly, not just an id/versionNumber stub - Finance/Merchandiser's only lens into a Tech Pack
   is through this record, and the old `ProtoRequestDetailPage` following up with
   `GET /tech-packs/:id` would 404 for exactly those two roles. Rewrote the page to stop making
   that second call entirely.
2. **Migration backfill.** Adding `ProjectMember` to a database with real existing Projects meant
   every one of them would have gone dark to everyone but the see-all roles the moment the
   migration ran - including the people who actually did the work on it. Hand-edited the migration
   (after `--create-only`, same procedure as every schema change here) to backfill, per Project,
   its creator plus everyone who ever uploaded a version, remarked, confirmed, or decided on one of
   its Tech Packs - history rows attributed to the creator, the closest honest "who added whom"
   available after the fact.
3. **`hasPendingNewerVersion`.** A Tech Pack can legitimately have a confirmed v1 and an
   unconfirmed v2 sitting on top of it (nothing stops uploading a new version after a confirm, only
   before a decision) - Management's shaped view only shows confirmed versions, so without this
   flag they'd see v1 as "the latest" and a Decide button that would 409 the moment they clicked it
   (the API's pre-existing "not the latest version" check). Added the flag to the response and
   wired `canDecide`/`TechPackActions` to hide the form and explain why instead.
4. **Endpoint x role inventory table in ADR 0013**, with the matrix backed by a new
   `tests/visibility.test.ts` - one `it.each` row per cell that isn't a trivial restatement of an
   adjacent one.
5. **Finance/Merchandiser's Project page has no Tech Packs section at all** - the API already
   returns an empty list for them either way, but showing "No tech packs yet." would wrongly
   suggest there genuinely are none, rather than that this role just can't see them.
6. **The member-add picker needed its own endpoint.** PMO manages membership but `GET /users` is
   ADMIN-only (ADR 0011, no exceptions) - rather than reopening that, added a narrow
   `GET /projects/:id/members/candidates` (PMO/ADMIN only) returning exactly what the picker needs:
   active, non-see-all, not-already-a-member users.

### A real gap found while writing the ADR's own test matrix

`assertProjectVisible` only checked existence as a side effect of the membership lookup - which
never runs for a see-all role, since `canSeeAllProjects` returns first. A PMO/ADMIN calling, say,
`POST /projects/:id/members` on a genuinely nonexistent `projectId` would sail past the visibility
check and then hit a raw Prisma foreign-key error trying to write the membership row - a 500, not
the 404 everything else in this ADR promises. Fixed by giving `assertProjectVisible` its own
explicit existence check (`projectRepository.exists`), run before the see-all short-circuit, for
every role. Caught by writing a test for exactly this case rather than assuming the asymmetry
didn't matter.
